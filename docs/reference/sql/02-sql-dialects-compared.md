# SQL Dialects Compared

> Part of the [SQL & PostgreSQL reference library](README.md) · Last researched: 2026-10-05 · Targets PostgreSQL 14–18 (19 beta noted where relevant)

**What this covers.** How the same task is written in PostgreSQL, MySQL/MariaDB, SQLite, SQL Server (T-SQL) and Oracle, plus a short look at analytical engines (DuckDB, BigQuery, Snowflake, ClickHouse) and at the SQL standard. Use it to translate SQL from one engine to another, to spot differences that change results without any error, and to decide when portable SQL is worth the effort. PostgreSQL is the reference dialect of this library; standard SQL basics are in [01-sql-fundamentals.md](01-sql-fundamentals.md).

## Key rules (TL;DR)

1. Test every query on the real target engine and version: "it works in PostgreSQL" proves nothing about MySQL, SQLite, SQL Server or Oracle.
2. Write identifiers in lowercase `snake_case` and never quote them: each engine folds unquoted names differently, and quoting freezes the case.
3. Use single quotes for strings only. Double quotes mean identifiers in standard SQL, but strings in default MySQL and (as a fallback) in SQLite.
4. Use `||` only where it means concatenation (PostgreSQL, SQLite, Oracle, SQL Server 2025+). In MySQL it means `OR` unless `PIPES_AS_CONCAT` is set: use `CONCAT()` there.
5. Handle NULL explicitly: `CONCAT`, `||`, `GREATEST`, `LEAST` and the empty string `''` behave differently per engine (Oracle stores `''` as NULL).
6. Always give paginated queries a full `ORDER BY` and say where NULLs go: the default NULL position differs per engine.
7. Translate row limiting carefully: `LIMIT/OFFSET` (PostgreSQL, MySQL, SQLite), `OFFSET … FETCH` (standard: PostgreSQL, SQL Server 2012+, Oracle 12c+), `TOP` (SQL Server).
8. Use each engine's native upsert (`ON CONFLICT`, `ON DUPLICATE KEY UPDATE`, `MERGE`) and know its race conditions. Never use `REPLACE` or `INSERT OR REPLACE` as an upsert.
9. In PostgreSQL, prefer `INSERT … ON CONFLICT` over `MERGE` for concurrent upserts. In SQL Server, add `HOLDLOCK` to an upsert `MERGE`, or avoid `MERGE`.
10. Get generated values back with `RETURNING` (PostgreSQL, SQLite 3.35+, MariaDB, Oracle `RETURNING INTO`) or `OUTPUT` (SQL Server). MySQL has neither: use `LAST_INSERT_ID()` or keys generated by the application.
11. Keep MySQL strict: leave `STRICT_TRANS_TABLES` and `ONLY_FULL_GROUP_BY` on, and never compare a string column with a number.
12. In SQLite, run `PRAGMA foreign_keys = ON` on every connection, and use `STRICT` tables (3.37+) when you want type checks.
13. Expect case-insensitive `=` on strings in MySQL and SQL Server by default, and case-sensitive `=` in PostgreSQL, Oracle and SQLite.
14. Store instants in a time-zone-aware type (`timestamptz`, `datetimeoffset`, `TIMESTAMP WITH TIME ZONE`) or as UTC; avoid MySQL `TIMESTAMP`, which stops in 2038.
15. Remember integer division: `7 / 2` is `3` in PostgreSQL, SQL Server and SQLite, but `3.5000` in MySQL and `3.5` in Oracle.
16. Do not expect DDL to roll back on MySQL or Oracle: DDL commits implicitly there. PostgreSQL, SQL Server and SQLite can roll most DDL back.
17. Know the default isolation level: READ COMMITTED (PostgreSQL, Oracle, SQL Server), REPEATABLE READ with gap locks (MySQL InnoDB), SERIALIZABLE (SQLite).
18. In MySQL (InnoDB) and SQL Server the primary key is usually the clustered index: use short, increasing keys (`bigint` identity, UUIDv7), not random UUIDv4.
19. Emulate missing features with standard SQL: `FILTER` → `CASE` inside the aggregate; `QUALIFY` → a derived table; MySQL `FULL JOIN` → `LEFT JOIN` + `UNION ALL` + anti-join.
20. Pass values as bind parameters instead of writing date, boolean or number literals: it removes most literal-syntax differences and prevents SQL injection.
21. Keep dialect-specific SQL in one layer (repository functions, views). Treat translators such as SQLGlot as a first draft, then review and test.
22. On analytical engines, think in partitions, sort keys and bytes scanned, not B-tree indexes, and check whether constraints are enforced at all.

## How to read this document

- Code without a label is PostgreSQL. Every other example starts with a comment such as `-- MySQL:` or `-- SQL Server (T-SQL):`.
- "MySQL" means MySQL 8.4 LTS and later. MariaDB is a fork of MySQL; it is mentioned only where it differs.
- Oracle Database 23ai was renamed **Oracle AI Database 26ai** in October 2025; 26ai is the 23ai code line plus release update 23.26 [16][17]. This document writes "Oracle 23ai+" for features of that family, and "Oracle 26ai" for newer features documented for 26ai (some need a late 23ai release update, `QUALIFY` needs 23.26 [17]).
- Version tags give the first version with the feature, for example "(PG 15+)", "(SQLite 3.35+)", "(SQL Server 2022+)".
- A "dialect" is the variant of SQL that one engine accepts: its syntax, functions, types and default behavior.

## 2. The SQL standard and what engines implement

The SQL standard is ISO/IEC 9075. It is large, and almost every feature is optional, so no engine implements all of it. Every engine also adds its own extensions. Two recent editions matter for daily work:

- **SQL:2016** added the SQL/JSON functions (`JSON_VALUE`, `JSON_QUERY`, `JSON_TABLE`, `IS JSON`) on JSON stored as text [20], `LISTAGG` for string aggregation [73], and row pattern matching (`MATCH_RECOGNIZE`).
- **SQL:2023** added a real `JSON` type, property graph queries (SQL/PGQ, a new Part 16 with `GRAPH_TABLE`), and many small conveniences [20].

| SQL:2023 feature [20] | PostgreSQL | MySQL | SQLite | SQL Server | Oracle |
|---|---|---|---|---|---|
| `JSON` data type (T801) | `json`, `jsonb` (long before the standard) | `JSON` | no type; JSON functions on text and JSONB blobs | `json` (2025+) [13] | `JSON` (21c+) |
| `GREATEST` / `LEAST` (T054) | yes, ignores NULLs [23] | yes, NULL if any argument is NULL | multi-argument `max()` / `min()` | yes (2022+) [14] | yes, NULL if any argument is NULL |
| `LPAD` / `RPAD` (T055) | yes | yes | no | no | yes |
| `ANY_VALUE` aggregate (T626) | PG 16+ [4] | `ANY_VALUE()` exists, but only to silence `ONLY_FULL_GROUP_BY` | no ("bare columns" instead) | no | yes |
| `UNIQUE NULLS [NOT] DISTINCT` (F292) | PG 15+ | no | no | no | no |
| Integer literals `0x1F`, `0o17`, `0b101` (T661) | PG 16+ [4] | `0x…`/`0b…` exist but are binary strings | `0x…` only | `0x…` is a binary constant | no |
| Underscores in numbers, `1_000_000` (T662) | PG 16+ [4] | no | no | no | no |
| Property graph queries, `GRAPH_TABLE` (SQL/PGQ) | no (not in the 19 beta release notes [2]) | no | no | no (has its own `MATCH` graph syntax) | yes (23ai+) |

**What this means in practice.** "Standard SQL" is a direction, not a guarantee. A standard feature can be missing, renamed, or behave differently (see `GREATEST` and NULLs above). Check each engine's documentation before you rely on a feature.

## 3. Identifiers, literals, comments and concatenation

An **identifier** is the name of a table, column, index or other object. A **literal** is a constant written in the query, such as `'Paris'` or `42`.

| Topic | PostgreSQL | MySQL / MariaDB | SQLite | SQL Server | Oracle |
|---|---|---|---|---|---|
| Unquoted names fold to | lower case [21] | not folded; table names are case-sensitive or not depending on the OS (`lower_case_table_names`), column names never [24] | not folded; names are case-insensitive | not folded; case sensitivity follows the database collation (usually insensitive) | UPPER case [62] |
| Quote an identifier with | `"name"` | `` `name` ``, or `"name"` with `ANSI_QUOTES` [26] | `"name"` (also accepts `` `name` `` and `[name]`) | `[name]`, or `"name"` with `QUOTED_IDENTIFIER ON` | `"NAME"` |
| Max identifier length | 63 bytes; longer names are truncated [21] | 64 characters | no practical limit | 128 characters | 128 bytes (12.2+) [62] |
| String literal | `'text'`; `E'a\nb'` for C escapes; `$$text$$` [21] | `'text'` or `"text"`; backslash escapes are on by default [26] | `'text'`; `"text"` may be read as a string if no column matches [46] | `'text'`; `N'text'` for Unicode (`nvarchar`) | `'text'`; `q'[it's]'` alternative quoting |
| Unicode escape | `U&'\0041'` [21] | none | `unistr('\u0041')` (3.50+) [48] | `NCHAR(65)`; `UNISTR()` (2025+) [13] | `UNISTR('\0041')` |
| Concatenation | `\|\|`, `concat()` | `CONCAT()`; `\|\|` means OR (deprecated) unless `PIPES_AS_CONCAT` [26][27] | `\|\|`; `concat()` (3.44+) [12] | `+`, `CONCAT()`; `\|\|` (2025+) [13] | `\|\|`, `CONCAT()` (2+ arguments in 23ai) [64] |
| NULL in concatenation | `\|\|` gives NULL; `concat()` skips NULLs | `CONCAT()` gives NULL; `CONCAT_WS()` skips NULLs [28] | `\|\|` gives NULL [47] | `+` gives NULL; `CONCAT()` skips NULLs | NULL acts as an empty string [63] |
| Comments | `--`, `/* */` (can nest) [21] | `#`, `-- ` (a space is required after `--`), `/* */`, `/*! … */` runs only on MySQL [25] | `--`, `/* */` | `--`, `/* */` (can nest) | `--`, `/* */`; `/*+ … */` are optimizer hints |

### Identifier case: the most common migration error

PostgreSQL folds unquoted names to lower case; the standard and Oracle fold to upper case [21][62]. If a tool creates a table with a quoted mixed-case name, every query must quote it forever.

```sql
-- Bad: quoted mixed-case name
CREATE TABLE "OrderItems" (id bigint);
SELECT * FROM orderitems;      -- ERROR: relation "orderitems" does not exist
SELECT * FROM "OrderItems";    -- works, but now every query needs quotes

-- Good: lowercase snake_case, never quoted
CREATE TABLE order_items (id bigint);
SELECT * FROM ORDER_ITEMS;     -- works: folded to order_items
```

Prisma names tables after models and quotes them, so a model `OrderItem` becomes the table `"OrderItem"` in PostgreSQL. Map models to lowercase names (`@@map("order_items")`) so raw SQL stays simple; see [15-postgres-from-typescript.md](15-postgres-from-typescript.md).

MySQL adds an operating-system trap: on Linux table names are case-sensitive (`lower_case_table_names = 0`), on Windows and macOS they are not (1 and 2), and the setting cannot change after the server is initialized [24]. Code that works on a developer's Mac can fail on a Linux server.

### Strings and escapes

- PostgreSQL treats a backslash in `'…'` as a normal character (`standard_conforming_strings` is on by default since 9.1); use `E'…'` for C-style escapes [21].
- MySQL treats a backslash as an escape character by default, so `'C:\new'` contains a newline. `NO_BACKSLASH_ESCAPES` turns this off [26]. Bind parameters avoid the problem completely.
- SQL Server needs the `N` prefix for Unicode literals: `N'Zoë'`. Without it, characters outside the database code page can be lost.
- MySQL `CONCAT('a', NULL)` returns NULL, while SQL Server `CONCAT('a', NULL)` returns `'a'`, and Oracle `'a' || NULL` returns `'a'` [28][63].

```sql
-- PostgreSQL, SQLite, Oracle, SQL Server 2025+: full name that survives NULLs
SELECT COALESCE(first_name, '') || ' ' || COALESCE(last_name, '') AS full_name FROM users;
-- MySQL: CONCAT_WS(' ', first_name, last_name)   (skips NULLs; plain CONCAT returns NULL)
-- SQL Server 2022 and older: CONCAT(first_name, ' ', last_name)   (NULL becomes '')
```

## 4. Keys: identity columns, sequences and UUIDs

| Need | PostgreSQL | MySQL / MariaDB | SQLite | SQL Server | Oracle |
|---|---|---|---|---|---|
| Auto-numbered key | `bigint GENERATED ALWAYS AS IDENTITY`; `serial` is legacy | `BIGINT AUTO_INCREMENT` | `INTEGER PRIMARY KEY` (alias of the rowid) | `bigint IDENTITY(1,1)` | `NUMBER GENERATED ALWAYS AS IDENTITY` (12c+) |
| Sequence object | `CREATE SEQUENCE`; `nextval('s')` | MySQL: none. MariaDB 10.3+: `CREATE SEQUENCE`, `NEXT VALUE FOR s` | none | `CREATE SEQUENCE` (2012+); `NEXT VALUE FOR s` | `CREATE SEQUENCE`; `s.NEXTVAL` |
| Read the new key | `RETURNING id` | `LAST_INSERT_ID()` | `RETURNING id` (3.35+); `last_insert_rowid()` | `OUTPUT inserted.id`; `SCOPE_IDENTITY()` | `RETURNING id INTO :v` |
| Random UUID | `gen_random_uuid()`; `uuidv4()` (PG 18+) [1] | MySQL `UUID()` returns a version-1 string; MariaDB 11.7+ adds `UUID_v4()` [89] | none built in; generate in the app [48] | `NEWID()` | `SYS_GUID()` (RAW(16)); `UUID()` (late 23ai/26ai) [15] |
| Time-ordered UUID | `uuidv7()` (PG 18+) [1] | `UUID_TO_BIN(UUID(), 1)` reorders the time bytes; MariaDB 11.7+ `UUID_v7()` [89] | generate in the app | `NEWSEQUENTIALID()` (only as a column `DEFAULT`) | generate in the app |
| UUID column type | `uuid` | MySQL: `BINARY(16)`; MariaDB 10.7+: `UUID` | `BLOB` or `TEXT` | `uniqueidentifier` | `RAW(16)` |

The same `orders` table in each dialect:

```sql
CREATE TABLE orders (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  public_id   uuid NOT NULL DEFAULT uuidv7() UNIQUE,  -- PG 18+; use gen_random_uuid() on PG 14–17
  customer_id bigint NOT NULL,
  total       numeric(12,2) NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);
```

```sql
-- MySQL 8.0.13+ (expression defaults)
CREATE TABLE orders (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
  public_id   BINARY(16) NOT NULL DEFAULT (UUID_TO_BIN(UUID(), 1)) UNIQUE,
  customer_id BIGINT NOT NULL,
  total       DECIMAL(12,2) NOT NULL,
  created_at  DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)  -- set the session time_zone to UTC
);
```

```sql
-- SQLite 3.37+ (STRICT table)
CREATE TABLE orders (
  id          INTEGER PRIMARY KEY,          -- alias of the rowid, assigned automatically
  public_id   BLOB NOT NULL UNIQUE,         -- UUID generated by the application
  customer_id INTEGER NOT NULL,
  total_cents INTEGER NOT NULL,             -- no exact decimal type: store cents
  created_at  TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%fZ', 'now'))
) STRICT;
```

```sql
-- SQL Server (T-SQL)
CREATE TABLE dbo.orders (
  id          bigint IDENTITY(1,1) NOT NULL CONSTRAINT pk_orders PRIMARY KEY,
  public_id   uniqueidentifier NOT NULL CONSTRAINT df_orders_public_id DEFAULT NEWSEQUENTIALID(),
  customer_id bigint NOT NULL,
  total       decimal(12,2) NOT NULL,
  created_at  datetime2(3) NOT NULL CONSTRAINT df_orders_created_at DEFAULT SYSUTCDATETIME(),
  CONSTRAINT uq_orders_public_id UNIQUE (public_id)
);
```

```sql
-- Oracle 12c+
CREATE TABLE orders (
  id          NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  public_id   RAW(16) DEFAULT SYS_GUID() NOT NULL UNIQUE,
  customer_id NUMBER NOT NULL,
  total       NUMBER(12,2) NOT NULL,
  created_at  TIMESTAMP WITH TIME ZONE DEFAULT SYSTIMESTAMP NOT NULL
);
```

**Why random UUID keys hurt some engines more.** InnoDB (MySQL, MariaDB) stores the table inside the primary-key B-tree, and every secondary index stores the primary key value [39]. A random UUIDv4 key makes each insert land on a random page: more page splits, more disk reads when the table is bigger than memory, and bigger secondary indexes [77]. SQL Server behaves the same way when the primary key is the clustered index (the default) [71]. Use a `bigint` identity as the clustered key and keep the UUID as a unique secondary column, or use a time-ordered UUID (UUIDv7, `UUID_TO_BIN(…, 1)`, `NEWSEQUENTIALID()`). PostgreSQL stores rows in a heap, so the effect is smaller, but UUIDv7 still gives better index locality; see [05-indexing.md](05-indexing.md) and [07-schema-design-and-patterns.md](07-schema-design-and-patterns.md).

**SQLite `AUTOINCREMENT` is not MySQL `AUTO_INCREMENT`** [46]. `INTEGER PRIMARY KEY` already assigns values. The `AUTOINCREMENT` keyword only prevents the reuse of ids from deleted rows, and it costs extra work.

## 5. Data type mapping

| Concept | PostgreSQL | MySQL / MariaDB | SQLite | SQL Server | Oracle |
|---|---|---|---|---|---|
| Integers | `smallint`, `integer`, `bigint` | `TINYINT` … `BIGINT`, optional `UNSIGNED` | `INTEGER` (stored in as few bytes as needed, up to 8) | `tinyint` (0–255), `smallint`, `int`, `bigint` | `NUMBER(p)`; `INTEGER` means `NUMBER(38)` |
| Exact decimal | `numeric(p,s)` | `DECIMAL(p,s)` | none: `NUMERIC` affinity stores an integer or a float | `decimal(p,s)` | `NUMBER(p,s)` |
| Floating point | `real`, `double precision` | `FLOAT`, `DOUBLE` | `REAL` (8 bytes) | `real`, `float` | `BINARY_FLOAT`, `BINARY_DOUBLE` |
| Boolean | `boolean` | `BOOLEAN` is an alias of `TINYINT(1)` | integers 0/1; `TRUE`/`FALSE` keywords since 3.23 [46] | `bit` | `BOOLEAN` (23ai+) [15]; before: `NUMBER(1)` |
| Variable text | `text`, `varchar(n)` | `VARCHAR(n)`, `TEXT`, `MEDIUMTEXT`, `LONGTEXT` | `TEXT`; declared lengths are not enforced [46] | `varchar(n\|max)`, `nvarchar(n\|max)` | `VARCHAR2(n)`: 4,000 bytes by default, 32,767 with `MAX_STRING_SIZE = EXTENDED` [65]; `CLOB` |
| Unicode | database encoding (use UTF8) | use `utf8mb4`; `utf8` means the deprecated 3-byte `utf8mb3` | UTF-8 or UTF-16 | `nvarchar` (UTF-16), or `varchar` with a UTF-8 collation (2019+) | `VARCHAR2` in an AL32UTF8 database, or `NVARCHAR2` |
| Date | `date` | `DATE` | `TEXT` `'YYYY-MM-DD'` | `date` | `DATE` (always includes a time of day) |
| Date and time, no zone | `timestamp` | `DATETIME(6)` | `TEXT` (ISO 8601), `INTEGER` (Unix time) or `REAL` (Julian day) [46] | `datetime2(n)` | `TIMESTAMP` |
| Absolute instant | `timestamptz` (stored as UTC, shown in the session zone) | `TIMESTAMP` (converted to UTC; range 1970–2038) [30] | UTC text or Unix time | `datetimeoffset` | `TIMESTAMP WITH TIME ZONE`, `TIMESTAMP WITH LOCAL TIME ZONE` |
| Interval | `interval` | none (only `INTERVAL` in expressions) | none | none | `INTERVAL YEAR TO MONTH`, `INTERVAL DAY TO SECOND` |
| JSON | `jsonb` (binary), `json` (text) | `JSON` (binary); MariaDB: `JSON` is `LONGTEXT` plus a validity check | functions on `TEXT`; JSONB blob format (3.45+) [12] | `json` (2025+) [13]; before: `nvarchar(max)` | `JSON` (21c+) |
| Binary | `bytea` | `VARBINARY`, `BLOB` | `BLOB` | `varbinary(n\|max)` | `RAW(n)`, `BLOB` |
| Arrays | native (`text[]`, `int[]`) | none (use JSON or a child table) | none | none | `VARRAY`, nested tables (mostly for PL/SQL) |
| Enumerations | `CREATE TYPE … AS ENUM` | `ENUM('a','b')` column type | `CHECK (col IN (…))` | `CHECK` | `CHECK`; SQL domains (23ai+) [15] |
| Vectors (embeddings) | `vector` from the pgvector extension, see [12-full-text-and-vector-search.md](12-full-text-and-vector-search.md) | MySQL 9.x `VECTOR`; MariaDB 11.7+ `VECTOR` | extensions | `vector` (2025+) [13] | `VECTOR` (23ai+) |

### Type gotchas when moving data

- **MySQL `TIMESTAMP`** is converted from the session time zone to UTC on write and back on read, and its range ends at `2038-01-19 03:14:07` UTC [30]. `DATETIME` is not converted at all. Prefer `DATETIME(6)` that always holds UTC, and set the connection time zone explicitly.
- **Oracle `DATE`** includes hours, minutes and seconds. `WHERE created = DATE '2026-10-05'` misses every row that is not exactly at midnight. Use a range: `created >= DATE '2026-10-05' AND created < DATE '2026-10-06'`.
- **SQLite affinity**: a declared type is only a hint. `'abc'` fits in an `INTEGER` column and 2,000 characters fit in `VARCHAR(50)` [46]. `STRICT` tables (3.37+) reject wrong types [46].
- **Money**: never use floating point. SQLite has no exact decimal, so store integer cents.
- **Booleans**: drivers and ORMs map `TINYINT(1)`, `bit` and `NUMBER(1)` to booleans in different ways. Test the round trip.

## 6. Row limiting and pagination

| Task | PostgreSQL | MySQL / MariaDB | SQLite | SQL Server | Oracle |
|---|---|---|---|---|---|
| First 10 rows | `LIMIT 10` or `FETCH FIRST 10 ROWS ONLY` | `LIMIT 10` | `LIMIT 10` | `TOP (10)`, or `OFFSET 0 ROWS FETCH NEXT 10 ROWS ONLY` (2012+) | `FETCH FIRST 10 ROWS ONLY` (12c+) |
| Skip 20, take 10 | `LIMIT 10 OFFSET 20` or `OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY` | `LIMIT 10 OFFSET 20` or `LIMIT 20, 10` | same as MySQL (comma form: offset first) [50] | `OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY` (requires `ORDER BY`) | `OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY` |
| Keep ties at the cut | `FETCH FIRST 10 ROWS WITH TIES` (PG 13+) | no | no | `TOP (10) WITH TIES` | `FETCH FIRST 10 ROWS WITH TIES` |
| Percent of rows | no | no | no | `TOP (10) PERCENT` | `FETCH FIRST 10 PERCENT ROWS ONLY` |
| Legacy method | — | — | — | `ROW_NUMBER()` in a derived table | `ROWNUM` (assigned before `ORDER BY`) [69] |

```sql
-- Standard syntax: PostgreSQL, SQL Server 2012+, Oracle 12c+ (not MySQL, not SQLite)
SELECT id, title
FROM documents
ORDER BY created_at DESC, id DESC
OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY;
```

```sql
-- Oracle, Bad: ROWNUM is assigned before ORDER BY, so this returns 10 random rows, then sorts them
SELECT * FROM orders WHERE ROWNUM <= 10 ORDER BY created_at DESC;

-- Oracle 12c+, Good:
SELECT * FROM orders ORDER BY created_at DESC FETCH FIRST 10 ROWS ONLY;
```

Notes:

- Add a unique column (such as `id`) as the last `ORDER BY` key. Otherwise rows with equal sort values can move between pages.
- `OFFSET` reads and throws away the skipped rows, so deep pages get slow in every engine. Use keyset pagination instead; the patterns are in [04-query-patterns-and-antipatterns.md](04-query-patterns-and-antipatterns.md).
- MySQL rejects `LIMIT` inside `IN`/`ALL`/`ANY`/`SOME` subqueries (error 1235) [33]. Rewrite with a join to a derived table.
- SQL Server and Oracle do not allow `ORDER BY` in a subquery, view or CTE unless it is needed by `TOP`/`OFFSET`/`FETCH` [57]. An `ORDER BY` inside a view never guarantees the order of the outer query in any engine.

## 7. Upsert: insert or update

An **upsert** inserts a row, or updates the existing row when the key already exists. Each engine spells it differently, and the concurrency rules differ. This section is about translation; the design patterns (conditional updates, `DO NOTHING`, batching) are in [04-query-patterns-and-antipatterns.md](04-query-patterns-and-antipatterns.md).

Example table: `product_stock (sku PRIMARY KEY, qty, updated_at)`. Add 5 units, or create the row.

```sql
-- PostgreSQL 9.5+: atomic for the conflict target
INSERT INTO product_stock (sku, qty, updated_at)
VALUES ('A-100', 5, now())
ON CONFLICT (sku) DO UPDATE
SET qty        = product_stock.qty + EXCLUDED.qty,
    updated_at = EXCLUDED.updated_at;
```

```sql
-- SQLite 3.24+: same idea; unqualified names in DO UPDATE mean the existing row
INSERT INTO product_stock (sku, qty, updated_at)
VALUES ('A-100', 5, CURRENT_TIMESTAMP)
ON CONFLICT (sku) DO UPDATE
SET qty        = qty + excluded.qty,
    updated_at = excluded.updated_at;
```

```sql
-- MySQL 8.0.19+: row alias (VALUES() is deprecated in MySQL)
INSERT INTO product_stock (sku, qty, updated_at)
VALUES ('A-100', 5, NOW(6)) AS new
ON DUPLICATE KEY UPDATE
  qty        = product_stock.qty + new.qty,
  updated_at = new.updated_at;

-- MariaDB: no row alias; use VALUES(col)
-- ... ON DUPLICATE KEY UPDATE qty = qty + VALUES(qty), updated_at = VALUES(updated_at);
```

```sql
-- SQL Server (T-SQL): HOLDLOCK is needed for a safe upsert; MERGE must end with ;
MERGE dbo.product_stock WITH (HOLDLOCK) AS t
USING (VALUES (N'A-100', 5, SYSUTCDATETIME())) AS s (sku, qty, updated_at)
  ON t.sku = s.sku
WHEN MATCHED THEN
  UPDATE SET t.qty = t.qty + s.qty, t.updated_at = s.updated_at
WHEN NOT MATCHED BY TARGET THEN
  INSERT (sku, qty, updated_at) VALUES (s.sku, s.qty, s.updated_at);
```

```sql
-- SQL Server (T-SQL): common alternative without MERGE
BEGIN TRANSACTION;
UPDATE dbo.product_stock WITH (UPDLOCK, SERIALIZABLE)
SET qty = qty + 5, updated_at = SYSUTCDATETIME()
WHERE sku = N'A-100';
IF @@ROWCOUNT = 0
  INSERT INTO dbo.product_stock (sku, qty, updated_at) VALUES (N'A-100', 5, SYSUTCDATETIME());
COMMIT TRANSACTION;
```

```sql
-- Oracle: the ON condition needs parentheses
MERGE INTO product_stock t
USING (SELECT 'A-100' AS sku, 5 AS qty FROM dual) s
  ON (t.sku = s.sku)
WHEN MATCHED THEN
  UPDATE SET t.qty = t.qty + s.qty, t.updated_at = SYSTIMESTAMP
WHEN NOT MATCHED THEN
  INSERT (sku, qty, updated_at) VALUES (s.sku, s.qty, SYSTIMESTAMP);
```

```sql
-- PostgreSQL 15+: standard MERGE (good for batch syncs, not for concurrent upserts)
MERGE INTO product_stock AS t
USING (VALUES ('A-100', 5)) AS s (sku, qty)
  ON t.sku = s.sku
WHEN MATCHED THEN
  UPDATE SET qty = t.qty + s.qty, updated_at = now()
WHEN NOT MATCHED THEN
  INSERT (sku, qty, updated_at) VALUES (s.sku, s.qty, now());
```

| Engine | Upsert syntax | Safe under concurrent inserts of the same key? | Main caveats |
|---|---|---|---|
| PostgreSQL | `INSERT … ON CONFLICT … DO UPDATE / DO NOTHING` | yes | `MERGE` (PG 15+) follows normal isolation rules and can fail with a unique violation when another session inserts the same key; the docs point to `ON CONFLICT` for that case [22]. `MERGE … RETURNING` and `WHEN NOT MATCHED BY SOURCE` are PG 17+ [3]. `ON CONFLICT DO SELECT … RETURNING` is (PG 19, beta — may change) [2]. |
| SQLite | `ON CONFLICT … DO UPDATE` (3.24+) [51] | yes (one writer at a time) | Several `ON CONFLICT` clauses and a target-less `DO UPDATE` need 3.35+ [51]. With `INSERT … SELECT`, add `WHERE true` before `ON CONFLICT` to avoid a parsing ambiguity [51]. |
| MySQL / MariaDB | `ON DUPLICATE KEY UPDATE` | yes, for the key that conflicts | It reacts to a conflict on *any* unique index; with several unique indexes the result can be surprising [31]. Affected rows are 1 (insert), 2 (update) or 0 (no change) [31]. |
| SQL Server | `MERGE` (2008+) | only with `WITH (HOLDLOCK)` [55] | Error 10713 without the final `;` [55]. Microsoft suggests separate statements under heavy concurrency [55]. Experts list many past `MERGE` bugs and advise avoiding it [75]. |
| Oracle | `MERGE` | no | Two sessions merging the same new key: the second one waits, then fails with ORA-00001 [76]. Catch `DUP_VAL_ON_INDEX` and update, or retry. `MERGE` cannot update a column used in its `ON` condition. |

**Never use delete-and-insert "upserts".** MySQL `REPLACE` deletes the old row and then inserts the new one [32]. SQLite `INSERT OR REPLACE` does the same. Columns you did not list get their default values, the row can get a new auto-increment id or rowid, and `ON DELETE CASCADE` foreign keys and delete triggers can fire. The affected-row count is 2 or more for a replacement [32].

Standard `MERGE` also differs between engines. SQL Server adds `WHEN NOT MATCHED BY SOURCE` (now also in PostgreSQL 17+), while Oracle has no `AND` condition on `WHEN` branches but supports a `DELETE WHERE` after an update [74][3].

## 8. Getting modified rows back: RETURNING and OUTPUT

`RETURNING` (or `OUTPUT`) sends back the rows that an `INSERT`, `UPDATE` or `DELETE` changed, in the same round trip. It is the best way to read generated ids and defaults.

| Engine | Syntax | Statements | Notes |
|---|---|---|---|
| PostgreSQL | `RETURNING *` or a column list; `old.col` / `new.col` (PG 18+) [1] | `INSERT`, `UPDATE`, `DELETE`, `MERGE` (PG 17+) [3] | Can feed another statement through a CTE: `WITH moved AS (DELETE … RETURNING *) INSERT … SELECT … FROM moved`. |
| SQLite 3.35+ | `RETURNING` [52] | `INSERT`, `UPDATE`, `DELETE` | Not usable as a subquery; rows come back in arbitrary order; no top-level aggregates; values are those before triggers run [52]. |
| MariaDB | `RETURNING` | `DELETE` (10.0.5+), `INSERT` / `REPLACE` (10.5+), single-table `UPDATE` (13.0+) [10][45] | No aggregate functions in `RETURNING` [45]. |
| MySQL | none | — | `LAST_INSERT_ID()` is per connection and returns the *first* id of a multi-row insert. Generate keys in the application, or `SELECT` again. |
| SQL Server | `OUTPUT inserted.col, deleted.col` [56] | `INSERT`, `UPDATE`, `DELETE`, `MERGE` (`$action`) | `OUTPUT` without `INTO` fails if the table has an enabled trigger for that action [56]. Rows are returned even if the statement then fails and rolls back [56]. |
| Oracle | `RETURNING col INTO variable` | `INSERT`, `UPDATE`, `DELETE` | Fills PL/SQL or bind variables, not a result set. 23ai+ can return both old and new values from `UPDATE` [15]. |

```sql
-- PostgreSQL 18+: before and after values in one statement
UPDATE accounts
SET balance = balance - 100
WHERE id = 42
RETURNING old.balance AS before, new.balance AS after;
```

```sql
-- SQL Server (T-SQL)
UPDATE dbo.accounts
SET balance = balance - 100
OUTPUT deleted.balance AS before, inserted.balance AS after
WHERE id = 42;
```

```sql
-- Oracle (PL/SQL)
DECLARE
  v_after accounts.balance%TYPE;
BEGIN
  UPDATE accounts SET balance = balance - 100
  WHERE id = 42
  RETURNING balance INTO v_after;
END;
/
```

```sql
-- MySQL: no RETURNING
INSERT INTO orders (customer_id, total) VALUES (7, 19.90);
SELECT LAST_INSERT_ID();   -- value for this connection only, safe under concurrency
```

## 9. UPDATE and DELETE with joins

Task: raise the priority of orders from VIP customers, and delete sessions of disabled users.

```sql
-- PostgreSQL: UPDATE … FROM and DELETE … USING
UPDATE orders AS o
SET priority = 'high'
FROM customers AS c
WHERE c.id = o.customer_id
  AND c.tier = 'vip';

DELETE FROM sessions AS s
USING users AS u
WHERE u.id = s.user_id
  AND u.disabled;
```

```sql
-- MySQL / MariaDB: multi-table syntax
UPDATE orders AS o
JOIN customers AS c ON c.id = o.customer_id
SET o.priority = 'high'
WHERE c.tier = 'vip';

DELETE s
FROM sessions AS s
JOIN users AS u ON u.id = s.user_id
WHERE u.disabled = 1;
```

```sql
-- SQLite 3.33+: UPDATE … FROM; DELETE has no join syntax
UPDATE orders
SET priority = 'high'
FROM customers AS c
WHERE c.id = orders.customer_id
  AND c.tier = 'vip';

DELETE FROM sessions
WHERE user_id IN (SELECT id FROM users WHERE disabled = 1);
```

```sql
-- SQL Server (T-SQL): name the alias after UPDATE / DELETE
UPDATE o
SET o.priority = 'high'
FROM dbo.orders AS o
JOIN dbo.customers AS c ON c.id = o.customer_id
WHERE c.tier = 'vip';

DELETE s
FROM dbo.sessions AS s
JOIN dbo.users AS u ON u.id = s.user_id
WHERE u.disabled = 1;
```

```sql
-- Oracle 23ai+: direct joins; the target joins the source in WHERE, not with JOIN … ON [67]
UPDATE orders o
SET o.priority = 'high'
FROM customers c
WHERE c.id = o.customer_id
  AND c.tier = 'vip';

DELETE sessions s
FROM users u
WHERE u.id = s.user_id
  AND u.disabled = 1;
```

```sql
-- Portable form (all engines, all versions): a correlated EXISTS
UPDATE orders
SET priority = 'high'
WHERE EXISTS (SELECT 1 FROM customers c
              WHERE c.id = orders.customer_id AND c.tier = 'vip');
```

Notes:

- If the join matches several rows for one target row, `UPDATE … FROM` updates it once with one of the matches, and which one is not predictable. Make the join unique, or aggregate first.
- MySQL cannot select from the table it modifies in a subquery (error 1093), except through a materialized derived table [33].

## 10. Query features: CTEs, window functions, QUALIFY, FILTER, grouping, set operations

A **CTE** (common table expression) is a named subquery written with `WITH`. A **window function** computes a value over related rows (for example a running total) without collapsing them like `GROUP BY` does.

| Feature | PostgreSQL | MySQL / MariaDB | SQLite | SQL Server | Oracle |
|---|---|---|---|---|---|
| `WITH` (CTE) | yes | MySQL 8.0+, MariaDB 10.2+ | 3.8.3+ | yes | yes |
| Recursive CTE keyword | `WITH RECURSIVE` (required) | `WITH RECURSIVE` (required) [34] | `RECURSIVE` is optional [53] | plain `WITH`; `RECURSIVE` is an error | plain `WITH`; column list required |
| Recursion limit | none | `cte_max_recursion_depth`, default 1000 [34] | none; add a `LIMIT` as a guard [53] | `MAXRECURSION`, default 100; `OPTION (MAXRECURSION 0)` = no limit [57] | error on a cycle unless you add a `CYCLE` clause |
| Lateral subquery | `LATERAL` | `LATERAL` (MySQL 8.0.14+) | no | `CROSS APPLY` / `OUTER APPLY` | `LATERAL`, `CROSS/OUTER APPLY` (12c+) |
| Window functions | yes | MySQL 8.0+, MariaDB 10.2+ | 3.25+ | yes | yes |
| `QUALIFY` | no | no | no | no | 26ai [17][68] |
| `IGNORE NULLS` in window functions | (PG 19, beta — may change) [2] | no | no | `FIRST_VALUE`/`LAST_VALUE` (2022+) [14] | yes |
| Aggregate `FILTER (WHERE …)` | yes | no | 3.30+ [49] | no | 26ai [15][16] |
| `GROUPING SETS`, `CUBE`, `ROLLUP` | all three | `WITH ROLLUP` only; `GROUPING()` [35] | none | all three | all three |
| `GROUP BY ALL` | no | no | no | no | 23ai+ [15] |
| `INTERSECT` / `EXCEPT` | yes, with `ALL` | MySQL 8.0.31+; MariaDB 10.3+ | yes, without `ALL` | yes, without `ALL` | `INTERSECT`, `MINUS`; `EXCEPT` and `ALL` forms (21c+) |
| `FULL OUTER JOIN` | yes | no | 3.39+ [12] | yes | yes |
| `PIVOT` / `UNPIVOT` | no (`FILTER` or `crosstab()`) | no | no | yes | yes (11g+) |
| `IS [NOT] DISTINCT FROM` | yes | `<=>` (NULL-safe equal) | 3.39+ (also `IS`) [12] | 2022+ [14] | no (use `DECODE`) |

### Recursive CTEs

```sql
-- PostgreSQL, MySQL 8.0+, SQLite: WITH RECURSIVE
WITH RECURSIVE tree (id, parent_id, depth) AS (
  SELECT id, parent_id, 0 FROM categories WHERE parent_id IS NULL
  UNION ALL
  SELECT c.id, c.parent_id, t.depth + 1
  FROM categories AS c
  JOIN tree AS t ON c.parent_id = t.id
)
SELECT * FROM tree;
-- SQL Server and Oracle: the same query, written WITH tree (id, parent_id, depth) AS (...)
-- Oracle: also drop AS before table aliases (FROM categories c), Oracle rejects it
-- SQL Server: deeper than 100 levels needs OPTION (MAXRECURSION n) on the outer query
```

Recursive parts have extra rules. MySQL forbids aggregates, window functions, `GROUP BY`, `ORDER BY` and `DISTINCT` in the recursive `SELECT` [34]. SQL Server forbids `DISTINCT`, `GROUP BY`, `TOP`, outer joins and subqueries there [57]. SQLite forbids aggregates and window functions there [53].

### QUALIFY and its standard replacement

`QUALIFY` filters on the result of a window function, the way `HAVING` filters on an aggregate [68].

```sql
-- DuckDB, Snowflake, ClickHouse, Oracle 26ai: latest order per customer
SELECT customer_id, id, created_at
FROM orders
QUALIFY row_number() OVER (PARTITION BY customer_id ORDER BY created_at DESC) = 1;
```

```sql
-- Standard (all engines with window functions): a derived table
-- Table aliases without AS, because Oracle rejects "FROM orders AS o"
SELECT customer_id, id, created_at
FROM (
  SELECT o.customer_id, o.id, o.created_at,
         row_number() OVER (PARTITION BY o.customer_id ORDER BY o.created_at DESC) AS rn
  FROM orders o
) ranked
WHERE rn = 1;

-- PostgreSQL only: DISTINCT ON
SELECT DISTINCT ON (customer_id) customer_id, id, created_at
FROM orders
ORDER BY customer_id, created_at DESC;
```

### FILTER and the CASE emulation

`FILTER` is standard (SQL:2003) but rare; `CASE` inside the aggregate works everywhere [72].

```sql
-- PostgreSQL, SQLite 3.30+, Oracle 26ai, DuckDB
SELECT count(*)   FILTER (WHERE status = 'paid') AS paid_orders,
       sum(total) FILTER (WHERE status = 'paid') AS paid_total
FROM orders;

-- Portable: CASE inside the aggregate
SELECT count(CASE WHEN status = 'paid' THEN 1 END)     AS paid_orders,
       sum(CASE WHEN status = 'paid' THEN total END)   AS paid_total
FROM orders;
```

Write `count(CASE WHEN … THEN 1 END)` with no `ELSE`. `ELSE 0` would count every row, because `count` counts all non-NULL values [72].

### Lateral joins: top 3 orders per customer

```sql
-- PostgreSQL, MySQL 8.0.14+
SELECT c.id, o.id AS order_id, o.total
FROM customers AS c
CROSS JOIN LATERAL (
  SELECT id, total FROM orders
  WHERE orders.customer_id = c.id
  ORDER BY total DESC
  LIMIT 3
) AS o;
```

```sql
-- SQL Server (T-SQL). Oracle 12c+ also accepts CROSS APPLY: use FETCH FIRST 3 ROWS ONLY and no AS before aliases
SELECT c.id, o.id AS order_id, o.total
FROM dbo.customers AS c
CROSS APPLY (
  SELECT TOP (3) id, total FROM dbo.orders
  WHERE orders.customer_id = c.id
  ORDER BY total DESC
) AS o;
```

### FULL OUTER JOIN in MySQL

```sql
-- MySQL / MariaDB: emulate FULL OUTER JOIN with LEFT JOIN + anti-join
SELECT a.sku, a.qty AS warehouse_qty, b.qty AS shop_qty
FROM warehouse_stock AS a
LEFT JOIN shop_stock AS b ON b.sku = a.sku
UNION ALL
SELECT b.sku, NULL, b.qty
FROM shop_stock AS b
WHERE NOT EXISTS (SELECT 1 FROM warehouse_stock AS a WHERE a.sku = b.sku);
```

Use `UNION ALL` plus the anti-join, not `LEFT JOIN … UNION … RIGHT JOIN`: plain `UNION` also removes real duplicate rows.

### PIVOT

```sql
-- SQL Server (T-SQL)
SELECT customer_id, [paid], [refunded]
FROM (SELECT customer_id, status, total FROM dbo.orders) AS src
PIVOT (SUM(total) FOR status IN ([paid], [refunded])) AS p;

-- Oracle
SELECT *
FROM (SELECT customer_id, status, total FROM orders)
PIVOT (SUM(total) FOR status IN ('paid' AS paid, 'refunded' AS refunded));
```

```sql
-- PostgreSQL (and SQLite 3.30+): FILTER; use CASE in MySQL
SELECT customer_id,
       sum(total) FILTER (WHERE status = 'paid')     AS paid,
       sum(total) FILTER (WHERE status = 'refunded') AS refunded
FROM orders
GROUP BY customer_id;
```

PostgreSQL also has `crosstab()` in the `tablefunc` extension, but `FILTER` is simpler and needs no extension.

### Collations: who compares case-insensitively

A **collation** is the set of rules that decides how strings sort and compare (case, accents, trailing spaces).

| | PostgreSQL | MySQL | SQLite | SQL Server | Oracle |
|---|---|---|---|---|---|
| `'abc' = 'ABC'` by default | false | true: default `utf8mb4_0900_ai_ci` is accent- and case-insensitive [37] | false | true on most installs (default depends on the OS locale; US English is `SQL_Latin1_General_CP1_CI_AS`) | false |
| Case-insensitive options | `ILIKE`; `lower(col) = lower($1)` with an expression index; `citext`; nondeterministic ICU collations (PG 12+; `LIKE` support PG 18+) [1] | `_ci` is the default; `_cs` or `_bin` for case-sensitive | `COLLATE NOCASE` (ASCII only) | `COLLATE …_CI_…` / `…_CS_…` per column or expression | `NLS_COMP=LINGUISTIC` + `NLS_SORT=BINARY_CI`; column collations (12.2+) |
| `LIKE` case | sensitive | follows the collation (insensitive by default) | insensitive for ASCII, sensitive beyond ASCII [47] | follows the collation | sensitive |
| Trailing spaces in `=` | significant for `text`/`varchar` | ignored with `PAD SPACE` collations, significant with `NO PAD` (all `0900` collations) [38] | significant | ignored for `=`; in `LIKE`, trailing spaces in the pattern count [59] | significant for `VARCHAR2`; ignored between `CHAR` values |

Consequences when you move data:

- A unique index on `email` in MySQL rejects `Ana@x.com` when `ana@x.com` exists. PostgreSQL accepts both. After a migration from MySQL, you may see "duplicates" that differ only by case. Normalize (`lower(email)`) or add a unique index on `lower(email)`.
- MySQL `utf8mb4_0900_ai_ci` also ignores accents: `'resume' = 'résumé'` is true [37].
- PostgreSQL 18 adds `casefold()` for correct case-insensitive matching across languages [1].

```sql
-- PostgreSQL: case-insensitive unique email
CREATE UNIQUE INDEX users_email_lower_uq ON users (lower(email));
SELECT * FROM users WHERE lower(email) = lower($1);   -- uses the index
```

## 12. Date and time

| Task | PostgreSQL | MySQL | SQLite | SQL Server | Oracle |
|---|---|---|---|---|---|
| Now | `now()` = `CURRENT_TIMESTAMP` (start of transaction); `clock_timestamp()` (real time) | `NOW(6)` (start of statement); `UTC_TIMESTAMP(6)`; `SYSDATE()` (time of execution) | `CURRENT_TIMESTAMP` (UTC text); `unixepoch()` (3.38+) [12] | `SYSUTCDATETIME()`, `SYSDATETIMEOFFSET()`, `GETDATE()` | `SYSTIMESTAMP`; `CURRENT_TIMESTAMP` (session zone); `SYSDATE` (server clock, `DATE`) |
| Today | `CURRENT_DATE` | `CURRENT_DATE`, `CURDATE()` | `date('now')` (UTC) | `CAST(GETDATE() AS date)`; `CURRENT_DATE` (2025+) [13] | `TRUNC(SYSDATE)` |
| Add 7 days | `ts + interval '7 days'` | `ts + INTERVAL 7 DAY` | `datetime(ts, '+7 days')` | `DATEADD(day, 7, ts)` | `ts + 7` (`DATE`), `ts + INTERVAL '7' DAY` |
| Difference | `ts2 - ts1` (interval); `d2 - d1` (integer days) | `TIMESTAMPDIFF(SECOND, ts1, ts2)`; `DATEDIFF(d2, d1)` (days) | `unixepoch(ts2) - unixepoch(ts1)`; `timediff()` (3.43+) [12] | `DATEDIFF(second, ts1, ts2)` (counts boundaries crossed) | `d2 - d1` (days as `NUMBER`); `ts2 - ts1` (`INTERVAL`) |
| Truncate to month | `date_trunc('month', ts)` | `DATE_FORMAT(ts, '%Y-%m-01')` (a string) | `date(ts, 'start of month')` | `DATETRUNC(month, ts)` (2022+) [14] | `TRUNC(ts, 'MM')` |
| Extract a part | `extract(year FROM ts)` | `EXTRACT(YEAR FROM ts)`, `YEAR(ts)` | `strftime('%Y', ts)` (text) | `DATEPART(year, ts)`, `YEAR(ts)` | `EXTRACT(YEAR FROM ts)` |
| Format | `to_char(ts, 'YYYY-MM-DD')` | `DATE_FORMAT(ts, '%Y-%m-%d')` | `strftime('%Y-%m-%d', ts)` | `CONVERT(char(10), ts, 23)`, `FORMAT(ts, 'yyyy-MM-dd')` | `TO_CHAR(ts, 'YYYY-MM-DD')` |
| Parse `05/10/2026` | `to_date(s, 'DD/MM/YYYY')` | `STR_TO_DATE(s, '%d/%m/%Y')` | ISO 8601 input only | `CONVERT(date, s, 103)`, `TRY_CONVERT` | `TO_DATE(s, 'DD/MM/YYYY')` |
| Convert time zone | `ts AT TIME ZONE 'Europe/Paris'` | `CONVERT_TZ(ts, '+00:00', 'Europe/Paris')` (named zones need the time zone tables loaded) | only `'localtime'` / `'utc'` modifiers | `ts AT TIME ZONE 'Romance Standard Time'` (2016+, Windows zone names) | `FROM_TZ(ts, 'UTC') AT TIME ZONE 'Europe/Paris'` |
| Day of week | `extract(isodow FROM d)`: 1 = Monday … 7 = Sunday | `DAYOFWEEK(d)`: 1 = Sunday … 7 = Saturday | `strftime('%w', d)`: 0 = Sunday | `DATEPART(weekday, d)`: depends on `SET DATEFIRST` | `TO_CHAR(d, 'D')`: depends on `NLS_TERRITORY` |

Gotchas:

- **"Now" is not the same instant everywhere.** PostgreSQL `now()` is fixed for the whole transaction; MySQL `NOW()` is fixed per statement; `clock_timestamp()` and MySQL `SYSDATE()` move during the statement.
- **Session time zone.** PostgreSQL shows `timestamptz` in the session `TimeZone`; MySQL converts `TIMESTAMP` with the session `time_zone` [30]. Set the zone explicitly on every connection (`SET TIME ZONE 'UTC'`; MySQL `SET time_zone = '+00:00'`) and convert for display in the application.
- **SQL Server `DATEDIFF` counts boundaries.** `DATEDIFF(year, '2025-12-31', '2026-01-01')` returns 1. Compute in a smaller unit when you need elapsed time.
- **Day-of-week numbers are not portable.** Even within one engine they depend on settings (SQL Server `DATEFIRST`, Oracle `NLS_TERRITORY`). Use ISO numbering (PostgreSQL `isodow`) or compare day names in a fixed language.
- **Oracle 26ai** adds `DATEADD`, `DATEDIFF` and `TIME_BUCKET`, which help when porting from SQL Server [15].
- **MySQL truncation** with `DATE_FORMAT` returns a string; wrap it in `CAST(… AS DATE)` before you compare it with dates.

| `GREATEST`/`LEAST` with a NULL argument | NULL is ignored [23] | result is NULL | multi-argument `max()`: result is NULL | NULL is ignored [88] | result is NULL |
| NULLs in `ORDER BY … ASC` | last | first | first | first | last |
| `NULLS FIRST` / `NULLS LAST` | yes | no | yes (3.30+) [50] | no | yes [70] |

### Oracle: the empty string is NULL

Oracle stores a zero-length string as NULL, and its documentation warns that this may change in a future release [63].

```sql
-- Oracle
SELECT CASE WHEN '' IS NULL THEN 'null' ELSE 'not null' END FROM dual;   -- 'null'
-- Consequences:
--   WHERE middle_name = ''   never matches
--   a NOT NULL column rejects ''
--   LENGTH('') is NULL, not 0
```

When you move data from Oracle, decide whether NULL means "unknown" or "empty", and convert consistently. When you move data to Oracle, empty strings silently become NULL.

### NULL ordering, portably

```sql
-- PostgreSQL, Oracle, SQLite 3.30+
SELECT id, due_date FROM tasks ORDER BY due_date NULLS LAST;

-- Portable (all five engines): put NULLs last for ascending order
SELECT id, due_date FROM tasks
ORDER BY CASE WHEN due_date IS NULL THEN 1 ELSE 0 END, due_date;
```

PostgreSQL can use an index created with the same `NULLS FIRST/LAST` order; Oracle accepts the clause in `ORDER BY` but not in index definitions [70].

## 15. Transactions and concurrency model

**MVCC** (multi-version concurrency control) means readers see a consistent snapshot of committed data, so they do not wait for writers. An **isolation level** says how much one transaction can see of other, concurrent transactions. **Transactional DDL** means `CREATE`/`ALTER`/`DROP` can be rolled back like data changes.

| | PostgreSQL | MySQL (InnoDB) | SQLite | SQL Server | Oracle |
|---|---|---|---|---|---|
| Default isolation | READ COMMITTED | REPEATABLE READ [41] | SERIALIZABLE [54] | READ COMMITTED [58] | READ COMMITTED [66] |
| How reads work | MVCC; old row versions stay in the table until vacuum | MVCC with undo logs; snapshot taken at the first read [41] | one writer at a time; in WAL mode readers keep a snapshot while a writer works [54] | shared locks by default; row versions in tempdb with RCSI or SNAPSHOT [58] | MVCC with undo; readers never block writers and writers never block readers [66] |
| Locking reads and writes | row locks; no gap locks | next-key and gap locks in REPEATABLE READ [41] | database-level write lock | key-range locks in SERIALIZABLE | row locks |
| SERIALIZABLE means | true serializability (SSI); retry on serialization errors | plain reads become locking reads | writes are serialized [54] | range locks, held to the end | snapshot isolation; ORA-08177 on conflict [66] |
| Transactional DDL | yes (most DDL) | no: DDL commits implicitly [40] | yes | yes (most DDL) [78] | no: DDL commits implicitly [78] |
| Autocommit | on unless you `BEGIN` | `autocommit = 1` by default | on unless you `BEGIN` | on unless `BEGIN TRANSACTION` or `IMPLICIT_TRANSACTIONS ON` | no server autocommit: a transaction starts with the first DML and ends with `COMMIT`, `ROLLBACK` or any DDL (client tools may autocommit) |

What changes when you port code:

- **MySQL → PostgreSQL.** In MySQL REPEATABLE READ, all plain reads of a transaction see one snapshot [41]. In PostgreSQL READ COMMITTED, each statement sees a fresh snapshot. Code that reads, computes and writes back needs `SELECT … FOR UPDATE` or a higher isolation level in PostgreSQL. Details are in [08-transactions-concurrency-locking.md](08-transactions-concurrency-locking.md).
- **MariaDB 12.3** turns `innodb_snapshot_isolation` on by default, which changes REPEATABLE READ semantics: test applications that depend on the old behavior [9].
- **SQL Server.** With the default locking READ COMMITTED, readers wait for writers. Many teams enable `READ_COMMITTED_SNAPSHOT` (it is the default in Azure SQL Database [58]), which behaves much like PostgreSQL.
- **Migrations.** PostgreSQL can run a whole migration in one transaction and roll it back on error. On MySQL and Oracle, each DDL statement commits, so a failed migration leaves a half-applied schema [40][78]. MySQL `CREATE TEMPORARY TABLE` does not commit, but it cannot be rolled back either [40]. See [10-safe-schema-migrations.md](10-safe-schema-migrations.md).
- **SQLite.** Only one writer at a time. Use WAL mode, keep write transactions short, and start transactions that will write with `BEGIN IMMEDIATE` to avoid `SQLITE_BUSY` errors when a reader tries to become a writer [54].

## 16. Indexing differences

A **heap table** stores rows in no particular order, and every index points to the row's location. A **clustered index** (an index-organized table) stores the rows themselves inside the primary-key B-tree [71].

| | PostgreSQL | MySQL (InnoDB) | SQLite | SQL Server | Oracle |
|---|---|---|---|---|---|
| Table storage | heap only [71] | clustered by the primary key [39][71] | B-tree keyed by rowid; `WITHOUT ROWID` tables cluster by the primary key | clustered index (the primary key by default) or heap [71] | heap by default; index-organized tables are optional [71] |
| A secondary index points to | the physical row location | the primary key value [39] | the rowid | the clustering key (or a row id for heaps) | the ROWID |
| Index types | B-tree, hash, GiST, SP-GiST, GIN, BRIN, plus extensions | B-tree, FULLTEXT, SPATIAL, multi-valued indexes on JSON arrays | B-tree; full-text and R-tree as virtual tables | B-tree, columnstore, full-text, spatial, XML; vector index (2025, preview) [13] | B-tree, bitmap, function-based, text, vector (23ai+) |
| Partial (filtered) index | `CREATE INDEX … WHERE …` | no | `WHERE …` (3.8+) | filtered index `WHERE …` | no syntax; index an expression that is NULL for excluded rows |
| Expression index | yes | functional key parts (8.0.13+) | yes (3.9+) | index a computed column | function-based index |
| Extra non-key columns (`INCLUDE`) | `INCLUDE` (PG 11+) | no (the primary key is always included) | no | `INCLUDE` | no |

### One goal, four syntaxes: "email unique among active users"

```sql
-- PostgreSQL / SQLite: partial unique index
CREATE UNIQUE INDEX users_email_active_uq ON users (email) WHERE deleted_at IS NULL;
```

```sql
-- SQL Server (T-SQL): filtered unique index
CREATE UNIQUE INDEX users_email_active_uq ON dbo.users (email) WHERE deleted_at IS NULL;
```

```sql
-- MySQL 8.0.13+: functional index that is NULL for deleted rows (NULLs never collide)
CREATE UNIQUE INDEX users_email_active_uq
  ON users ((CASE WHEN deleted_at IS NULL THEN email END));
```

```sql
-- Oracle: function-based index; rows where the expression is NULL are not indexed
CREATE UNIQUE INDEX users_email_active_uq
  ON users (CASE WHEN deleted_at IS NULL THEN email END);
```

Other differences that matter:

- **Clustered keys.** In InnoDB, every secondary index also stores the primary key, so a wide primary key makes every index bigger [39]. A random UUID primary key also scatters inserts across the whole table [77].
- **Bitmap indexes (Oracle)** suit low-cardinality columns in data warehouses. Avoid them on tables with concurrent writes, because one bitmap entry covers many rows.
- **Columnstore (SQL Server)** gives analytical scans on the same database; PostgreSQL needs extensions or a separate engine for that.
- **Heap vs clustered when porting.** A MySQL range scan on the primary key reads rows in key order for free. In PostgreSQL the same query uses a B-tree index plus heap lookups, and `CLUSTER` reorders the table only once. Design and maintenance details are in [05-indexing.md](05-indexing.md).

## 18. Procedural languages side by side

| | PostgreSQL | MySQL / MariaDB | SQLite | SQL Server | Oracle |
|---|---|---|---|---|---|
| Language | PL/pgSQL (others via extensions) | stored programs (SQL/PSM style); MySQL 9.x adds JavaScript stored programs (check your edition) | none: register functions from the host language | T-SQL | PL/SQL; JavaScript via MLE (23ai+) |
| Body delimiter | dollar quotes `$$ … $$` | `DELIMITER //` in the `mysql` client (not needed in drivers) | — | `GO` batch separator (client tools only) | `/` on its own line (SQL*Plus, SQLcl) |
| Raise an error | `RAISE EXCEPTION '…' USING ERRCODE = …` | `SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '…'` | `RAISE(ABORT, '…')` inside triggers only | `THROW 50001, N'…', 1` | `RAISE_APPLICATION_ERROR(-20001, '…')` |
| Catch an error | `BEGIN … EXCEPTION WHEN … THEN … END` | `DECLARE … HANDLER FOR …` | — | `BEGIN TRY … END TRY BEGIN CATCH … END CATCH` | `EXCEPTION WHEN … THEN` |

The same small routine in each language: fill a `calendar_days (cal_date PRIMARY KEY, is_weekend)` table for one year. It uses variables, `IF`, a loop, and error handling (reject a bad year; skip days that already exist).

```sql
-- PostgreSQL (PL/pgSQL)
CREATE OR REPLACE FUNCTION seed_calendar(p_year integer)
RETURNS integer
LANGUAGE plpgsql
AS $$
DECLARE
  v_day   date;
  v_count integer := 0;
BEGIN
  IF p_year NOT BETWEEN 1900 AND 2100 THEN
    RAISE EXCEPTION 'invalid year: %', p_year
      USING ERRCODE = 'invalid_parameter_value';
  END IF;

  v_day := make_date(p_year, 1, 1);
  WHILE v_day < make_date(p_year + 1, 1, 1) LOOP
    BEGIN
      INSERT INTO calendar_days (cal_date, is_weekend)
      VALUES (v_day, extract(isodow FROM v_day) IN (6, 7));
      v_count := v_count + 1;
    EXCEPTION
      WHEN unique_violation THEN
        NULL;  -- the day already exists: skip it
    END;
    v_day := v_day + 1;
  END LOOP;

  RETURN v_count;
END;
$$;

SELECT seed_calendar(2027);
```

```sql
-- MySQL / MariaDB (stored procedure)
DELIMITER //
CREATE PROCEDURE seed_calendar(IN p_year INT, OUT p_count INT)
BEGIN
  DECLARE v_day DATE;
  DECLARE v_dup INT DEFAULT 0;
  DECLARE CONTINUE HANDLER FOR 1062 SET v_dup = 1;   -- 1062 = duplicate key

  IF p_year NOT BETWEEN 1900 AND 2100 THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'invalid year';
  END IF;

  SET p_count = 0;
  SET v_day = MAKEDATE(p_year, 1);
  WHILE v_day < MAKEDATE(p_year + 1, 1) DO
    SET v_dup = 0;
    INSERT INTO calendar_days (cal_date, is_weekend)
    VALUES (v_day, DAYOFWEEK(v_day) IN (1, 7));      -- 1 = Sunday, 7 = Saturday
    IF v_dup = 0 THEN
      SET p_count = p_count + 1;
    END IF;
    SET v_day = v_day + INTERVAL 1 DAY;
  END WHILE;
END //
DELIMITER ;

CALL seed_calendar(2027, @n);
SELECT @n;
```

```sql
-- SQL Server (T-SQL)
CREATE OR ALTER PROCEDURE dbo.seed_calendar
  @year  int,
  @count int OUTPUT
AS
BEGIN
  SET NOCOUNT ON;

  IF @year NOT BETWEEN 1900 AND 2100
    THROW 50001, N'invalid year', 1;

  DECLARE @day date = DATEFROMPARTS(@year, 1, 1);
  SET @count = 0;

  WHILE @day < DATEFROMPARTS(@year + 1, 1, 1)
  BEGIN
    BEGIN TRY
      INSERT INTO dbo.calendar_days (cal_date, is_weekend)
      VALUES (@day,
              -- Saturday gives 0 and Sunday gives 1, whatever SET DATEFIRST says
              CASE WHEN (DATEPART(weekday, @day) + @@DATEFIRST) % 7 IN (0, 1) THEN 1 ELSE 0 END);
      SET @count += 1;
    END TRY
    BEGIN CATCH
      IF ERROR_NUMBER() NOT IN (2601, 2627)   -- not a duplicate key: re-throw
        THROW;
    END CATCH;
    SET @day = DATEADD(day, 1, @day);
  END;
END;
GO

DECLARE @n int;
EXEC dbo.seed_calendar @year = 2027, @count = @n OUTPUT;
SELECT @n AS inserted_days;
```

```sql
-- Oracle (PL/SQL)
CREATE OR REPLACE PROCEDURE seed_calendar(p_year IN PLS_INTEGER, p_count OUT PLS_INTEGER)
IS
  v_day DATE;
BEGIN
  IF p_year NOT BETWEEN 1900 AND 2100 THEN
    RAISE_APPLICATION_ERROR(-20001, 'invalid year: ' || p_year);
  END IF;

  p_count := 0;
  v_day := TO_DATE(p_year || '-01-01', 'YYYY-MM-DD');
  WHILE v_day < ADD_MONTHS(TO_DATE(p_year || '-01-01', 'YYYY-MM-DD'), 12) LOOP
    BEGIN
      INSERT INTO calendar_days (cal_date, is_weekend)
      VALUES (v_day,
              CASE WHEN TO_CHAR(v_day, 'DY', 'NLS_DATE_LANGUAGE=ENGLISH') IN ('SAT', 'SUN')
                   THEN 1 ELSE 0 END);
      p_count := p_count + 1;
    EXCEPTION
      WHEN DUP_VAL_ON_INDEX THEN
        NULL;  -- the day already exists: skip it
    END;
    v_day := v_day + 1;
  END LOOP;
END;
/

DECLARE
  n PLS_INTEGER;
BEGIN
  seed_calendar(2027, n);
  DBMS_OUTPUT.PUT_LINE(n || ' days inserted');
END;
/
```

```sql
-- SQLite: no stored procedures. Use one set-based statement (3.24+ for ON CONFLICT)
WITH RECURSIVE d(cal_date) AS (
  SELECT date('2027-01-01')
  UNION ALL
  SELECT date(cal_date, '+1 day') FROM d WHERE cal_date < '2027-12-31'
)
INSERT INTO calendar_days (cal_date, is_weekend)
SELECT cal_date, strftime('%w', cal_date) IN ('0', '6')
FROM d
WHERE true                         -- needed before ON CONFLICT in INSERT … SELECT [51]
ON CONFLICT (cal_date) DO NOTHING;
```

The loops above show syntax only. In real code, prefer one set-based statement in every engine. In PL/pgSQL, a block with an `EXCEPTION` clause starts a subtransaction each time it runs, which is slow inside a loop. The PostgreSQL set-based version:

```sql
INSERT INTO calendar_days (cal_date, is_weekend)
SELECT d::date, extract(isodow FROM d) IN (6, 7)
FROM generate_series(DATE '2027-01-01', DATE '2027-12-31', INTERVAL '1 day') AS g(d)
ON CONFLICT (cal_date) DO NOTHING;
```

## 19. DDL conveniences, temporary tables, generated columns and constraints

| | PostgreSQL | MySQL / MariaDB | SQLite | SQL Server | Oracle |
|---|---|---|---|---|---|
| `CREATE TABLE IF NOT EXISTS` | yes | yes | yes | no: `IF OBJECT_ID(N'dbo.t') IS NULL CREATE TABLE …` | 23ai+ [15] |
| `DROP TABLE IF EXISTS` | yes | yes | yes | 2016+ | 23ai+ [15] |
| Replace a view | `CREATE OR REPLACE VIEW` | `CREATE OR REPLACE VIEW` | `DROP VIEW` + `CREATE VIEW` | `CREATE OR ALTER VIEW` (2016 SP1+) | `CREATE OR REPLACE VIEW` |
| Rename a column | `ALTER TABLE t RENAME COLUMN a TO b` | same (MySQL 8.0+) | same (3.25+) | `EXEC sp_rename 'dbo.t.a', 'b', 'COLUMN'` | same |
| Temporary table | `CREATE TEMP TABLE` (per session; `ON COMMIT DROP` option) | `CREATE TEMPORARY TABLE` (per session; cannot be referenced twice in one query [44]) | `CREATE TEMP TABLE` (per connection) | `#t` (session), `##t` (global), table variables `@t` | `GLOBAL TEMPORARY TABLE` (permanent definition, private rows); `PRIVATE TEMPORARY TABLE ORA$PTT_…` (18c+) |
| Generated column | `GENERATED ALWAYS AS (expr) STORED`; `VIRTUAL` (PG 18+, now the default) [1] | `AS (expr) VIRTUAL` (default) or `STORED` | `AS (expr) VIRTUAL` (default) or `STORED` (3.31+) | computed column `AS (expr)`, optionally `PERSISTED` | virtual column `AS (expr)` (virtual only) |
| `CHECK` enforced | yes | MySQL 8.0.16+ (before: parsed and ignored) [43]; MariaDB 10.2.1+ | yes | yes | yes |
| `CHECK` and NULL | a NULL result passes (only FALSE fails) | same | same | same [61] | same |
| `UNIQUE` and NULLs | many NULLs allowed; `NULLS NOT DISTINCT` (PG 15+) | many NULLs | many NULLs | **only one NULL** per unique column [61] | rows whose key columns are all NULL are not indexed, so many are allowed |

Notes:

- **SQL Server unique + NULL.** Because a unique constraint allows only one NULL [61], use a filtered unique index (`WHERE col IS NOT NULL`) to get the behavior of the other engines.
- **MySQL temporary tables** fail with "Can't reopen table" when one query uses the same temporary table twice (for example a self-join); a CTE avoids the problem [44].
- **SQL Server table variables** (`DECLARE @t TABLE (…)`) live in tempdb like `#temp` tables but have no statistics, so the optimizer can misjudge them on large data. Prefer `#temp` tables for large sets.
- **Oracle global temporary tables** are created once (like normal tables) and every session sees only its own rows. Do not create them at run time.

## 20. Gotchas checklist when moving SQL between engines

| Gotcha | Where | What happens | What to do |
|---|---|---|---|
| Non-strict mode | MySQL without `STRICT_TRANS_TABLES` | `'abc'` becomes 0, long strings are cut, bad dates are adjusted; only warnings [26] | Keep the default strict `sql_mode` [26]; read warnings in tests. |
| Loose `GROUP BY` | MySQL with `ONLY_FULL_GROUP_BY` removed; MariaDB (not in its default `sql_mode`); SQLite "bare columns" [46] | Non-grouped columns return a value from an arbitrary row | Group by every selected column, or aggregate it explicitly. |
| String compared with a number | MySQL | `WHERE varchar_col = 0` matches every string that does not start with a digit (`'abc'` becomes 0) and cannot use the index [29] | Compare strings with strings; bind parameters with the right type. |
| Flexible typing | SQLite | Any value fits any column [46] | `STRICT` tables (3.37+), or `CHECK (typeof(col) = 'integer')`. |
| Foreign keys off | SQLite | Foreign keys are parsed but not enforced [46] | `PRAGMA foreign_keys = ON` on every connection. |
| NULL in a primary key | SQLite | A non-integer primary key accepts NULL [46] | Add `NOT NULL`, or use `STRICT` / `WITHOUT ROWID` tables. |
| `''` is NULL | Oracle | `= ''` never matches; `NOT NULL` rejects `''` [63] | Use `IS NULL`; agree on one meaning for "empty". |
| Identifier case | PostgreSQL vs Oracle; MySQL on Linux | "relation does not exist" after a migration [21][24][62] | Lowercase, unquoted names everywhere. |
| `AS` before a table alias | Oracle | `FROM orders AS o` is a syntax error | Write `FROM orders o`: it works in every engine (keep `AS` for column aliases). |
| Integer division | PostgreSQL, SQL Server, SQLite | `7 / 2` = 3 [47], while MySQL returns `3.5000` and Oracle `3.5` | `CAST(a AS numeric) / b`, or `a * 1.0 / b`; in MySQL use `DIV` for integer division. |
| NULL sort position | PostgreSQL and Oracle vs the others | Page contents change after a migration | Write `NULLS FIRST/LAST`, or the portable `CASE` key (section 13). |
| Booleans | SQL Server (`bit`, no boolean values), MySQL (`TINYINT`), Oracle before 23ai | Predicates cannot be selected; ORMs map types differently | `CASE WHEN … THEN 1 ELSE 0 END`; test the driver mapping. |
| `LIMIT` in subqueries | MySQL (`IN` subqueries) [33]; SQL Server (`ORDER BY` needs `TOP`/`OFFSET`) [57]; Oracle (`ROWNUM` before `ORDER BY`) [69] | Errors or wrong rows | Use a derived table, a join, or a window function. |
| Time zones | MySQL `TIMESTAMP` (session zone, ends 2038) [30]; SQL Server `datetime2` (no zone) | Times shift by the server's offset | Store UTC or zone-aware types; set the session zone on connect. |
| Case-insensitive defaults | MySQL, SQL Server | Unique conflicts and "duplicates" that differ only by case [37] | Normalize values, or choose collations on purpose. |
| Trailing spaces | MySQL `PAD SPACE` collations, SQL Server `=` | `'a' = 'a '` is true [38][59] | Trim input before storing. |
| Silent truncation of lists | MySQL `GROUP_CONCAT` | Result cut at 1024 bytes by default [36] | Raise `group_concat_max_len`, or use `JSON_ARRAYAGG`. |
| `\|\|` is OR | MySQL | `'a' \|\| 'b'` returns 0 [27] | Use `CONCAT()`. |
| Backslash escapes | MySQL | `'C:\new'` contains a newline [26] | Bind parameters; or `NO_BACKSLASH_ESCAPES`. |
| Implicit commit on DDL | MySQL, Oracle | Half-applied migrations [40][78] | One DDL step per migration; make scripts re-runnable. |
| CHECK ignored | MySQL before 8.0.16 | Constraints silently not enforced [43] | Upgrade; test that a bad row is rejected. |
| Recursion limits | MySQL (1000) [34], SQL Server (100) [57] | Deep hierarchies fail with an error | Raise `cte_max_recursion_depth` or use `OPTION (MAXRECURSION n)`. |
| Upsert races | SQL Server `MERGE`, Oracle `MERGE`, PostgreSQL `MERGE` | Duplicate-key errors under load [22][55][76] | `ON CONFLICT` in PostgreSQL; `HOLDLOCK` or update-then-insert in SQL Server; catch and retry in Oracle. |

## 21. Analytical engines: DuckDB, BigQuery, Snowflake, ClickHouse

Analytical (OLAP) engines store data by column, compress it, and scan it in parallel. They rarely use B-tree indexes. Instead they skip blocks of data using min/max metadata, partitions and sort keys. In the cloud, the bill depends on how much data a query reads.

| | DuckDB | BigQuery (GoogleSQL) | Snowflake | ClickHouse |
|---|---|---|---|---|
| Runs as | a library inside your process | serverless cloud service | cloud data warehouse | server or cluster, or cloud service |
| Indexes | not needed for scans | no classic indexes; search and vector indexes only [80] | none; metadata per micro-partition (50–500 MB of uncompressed data each) [81] | sparse primary index on the `ORDER BY` key, one entry per 8,192 rows by default [83] |
| How to make queries cheap | read only needed columns; filter early; use Parquet | partition (for example by day) and cluster (up to 4 columns) [80] | filter on columns that prune micro-partitions; clustering keys for very large tables [81] | choose the `ORDER BY` key well: low-cardinality columns first [83] |
| Cost model | your own CPU | bytes processed (on-demand pricing) [80] | warehouse running time | your own hardware or cloud compute |
| `PRIMARY KEY` / `UNIQUE` enforced | yes | no (informational only) | no; only `NOT NULL` is enforced [82] | no: the primary key is not unique [83] |
| `QUALIFY` | yes [79] | yes | yes | yes [84] |
| Nested and semi-structured types | `LIST`, `STRUCT`, `MAP`, `VARIANT` (1.5+) [18] | `ARRAY`, `STRUCT`, `JSON` | `VARIANT`, `OBJECT`, `ARRAY` | `Array`, `Tuple`, `Map`, `JSON` |
| Updates and deletes | normal DML | DML supported, best in batches | normal DML | "mutations" and lightweight deletes; design for inserts |
| Surprises | many "friendly SQL" extensions [79] | names and functions differ from PostgreSQL | unquoted identifiers are stored in UPPER case | unmatched outer-join cells get type defaults (0, `''`) instead of NULL unless `join_use_nulls = 1` [85]; columns are NOT NULL unless declared `Nullable(T)` |

```sql
-- DuckDB: "friendly SQL" [79]
SELECT * EXCLUDE (embedding) FROM chunks;                  -- every column except one
SELECT customer_id, sum(total) FROM orders GROUP BY ALL;   -- group by all non-aggregated columns
FROM 'events/*.parquet' SELECT count(*);                   -- FROM first; query files directly
SELECT t.*, p.price
FROM trades AS t
ASOF JOIN prices AS p
  ON t.symbol = p.symbol AND t.ts >= p.ts;                 -- last known price at trade time
```

```sql
-- BigQuery (GoogleSQL): partitioned and clustered table
CREATE TABLE shop.events (
  event_ts TIMESTAMP,
  user_id  STRING,
  payload  JSON
)
PARTITION BY DATE(event_ts)
CLUSTER BY user_id;
```

```sql
-- ClickHouse: the ORDER BY key decides what can be skipped
CREATE TABLE events (
  event_date Date,
  user_id    UInt64,
  event_type LowCardinality(String),
  payload    String
)
ENGINE = MergeTree
ORDER BY (event_type, event_date, user_id);
```

```sql
-- Snowflake: clustering key and VARIANT path access
ALTER TABLE events CLUSTER BY (TO_DATE(event_ts));
SELECT payload:customer.id::number AS customer_id FROM events;
```

Key tips:

1. Select only the columns you need: in a column store, `SELECT *` reads every column.
2. Filter on the partition, cluster or sort columns, or the engine scans everything.
3. Do not count on constraints: de-duplicate with `QUALIFY row_number() OVER (…) = 1` or in the load pipeline.
4. Batch writes; avoid row-by-row updates.
5. Re-check function behavior after upgrades. For example, DuckDB 1.5 changed `date_trunc` on a `DATE` to return a `TIMESTAMP` [18], and DuckDB 2.0 brings a new parser [19].
6. DuckDB is handy next to PostgreSQL for one-off analysis of exports and Parquet files; see [13-tools-by-use-case.md](13-tools-by-use-case.md).

## 22. Portability guidelines

**First, decide whether you need portability.** This project targets PostgreSQL only, so use PostgreSQL features freely, but keep them in one layer. Portability has a cost; pay it only where several engines must really run the same SQL.

### Prefer standard syntax when it costs nothing

| Prefer (standard) | Instead of | Caveat |
|---|---|---|
| `CASE WHEN … END` | `IF()`, `IIF()`, `DECODE()` | none |
| `COALESCE(a, b)` | `IFNULL`, `ISNULL`, `NVL` | none |
| `CAST(x AS type)` | `x::type`, `CONVERT()` | type names still differ |
| `CURRENT_TIMESTAMP` | `now()`, `GETDATE()`, `SYSDATE` | its exact meaning differs (section 12); `CURRENT_DATE` is SQL Server 2025+ only |
| `OFFSET … FETCH FIRST n ROWS ONLY` | `LIMIT`, `TOP`, `ROWNUM` | not in MySQL or SQLite |
| `JOIN … ON` | comma joins; Oracle `(+)` outer joins | none |
| `EXISTS (…)` | engine-specific `UPDATE … FROM` / `DELETE … USING` | none |
| `count(CASE WHEN … THEN 1 END)` | `FILTER` where it is missing | none |
| `'single quotes'` for strings | `"double quotes"` | none |
| `<>` | `!=` | `!=` works almost everywhere anyway |

Even standard functions are not universal: `SUBSTRING(s FROM 2 FOR 3)` fails on SQL Server and Oracle, and `GREATEST` treats NULLs differently (section 13).

### Keep dialect-specific code in one place

- Put SQL in repository functions or database views, not spread across the code base.
- Name dialect-only features in a comment (`-- PostgreSQL-specific: ON CONFLICT`), so a future port can find them.
- Pass values as bind parameters. The driver then handles date, boolean and number formats, and you avoid SQL injection; see [11-security.md](11-security.md).
- With Prisma, the query API generates the right SQL for each database, but `$queryRaw` text is sent as written and stays dialect-specific; see [15-postgres-from-typescript.md](15-postgres-from-typescript.md).

### Test on the real engine

Run tests against the same engine and major version as production, for example in a container. Do not use SQLite as a stand-in for PostgreSQL in tests: typing, NULL ordering, concurrency and many functions differ (sections 5, 12, 13, 15).

### Translation tools and their limits

**SQLGlot** is a Python library that parses SQL into a syntax tree and writes it back in another dialect; it supports over 30 dialects [86].

```python
import sqlglot

sqlglot.transpile("SELECT TOP 10 * FROM orders ORDER BY id", read="tsql", write="postgres")[0]
# 'SELECT * FROM orders ORDER BY id LIMIT 10'
```

Limits to keep in mind:

- It is "a transpiler, not a validator": its parser is lenient and accepts queries that a real engine rejects [86].
- Some translations are best-effort. It warns by default, and `unsupported_level` can turn warnings into errors [86].
- It translates syntax, not behavior: collations, NULL ordering, integer division, time zones, isolation and locking stay different.
- Procedural code (PL/pgSQL, T-SQL, PL/SQL) needs a manual rewrite.

Library-level alternatives exist too: jOOQ (Java) builds one query tree and renders it for each dialect, emulating missing features where it can [74]. Whatever tool you use, review the output and run it on the target engine. Tools for one-time migrations between engines are listed in [13-tools-by-use-case.md](13-tools-by-use-case.md).
