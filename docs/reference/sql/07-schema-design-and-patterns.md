# Schema Design and Data Modeling Patterns

> Part of the [SQL & PostgreSQL reference library](README.md) · Last researched: 2026-10-05 · Targets PostgreSQL 14–18 (19 beta noted where relevant)

**What this covers.** How to turn a business domain into PostgreSQL tables (design process, normalization, keys, constraints, naming, NULLs, time columns, column order), then proven patterns with schemas, queries, and trade-offs: trees, polymorphism, subtypes, soft delete, history, state machines, queues, outbox, counters, multi-tenancy, partitioning. It ends with anti-patterns and a review checklist. Types are in [03](03-postgresql-features-and-types.md), locking in [08](08-transactions-concurrency-locking.md), RLS in [11](11-security.md), safe rollout in [10](10-safe-schema-migrations.md).

## Key rules (TL;DR)

1. Start from the domain: list entities, invariants (rules that must always be true), and the top read/write paths before you write `CREATE TABLE`.
2. Normalize to 3NF first. Denormalize only with measured evidence, and name the source of truth and the refresh path of every copy.
3. Make every column `NOT NULL` unless you can say what NULL means for it.
4. Enforce invariants in the database with `CHECK`, `UNIQUE`, `FOREIGN KEY`, and `EXCLUDE`; validate in the app too, for friendly error messages.
5. Declare every foreign key, choose its `ON DELETE` action on purpose, and index the referencing columns.
6. Use `bigint GENERATED ALWAYS AS IDENTITY` or UUIDv7 primary keys; never `serial`, never `integer` for tables that grow, never random UUIDv4 as the key of a large write-heavy table.
7. Use UUIDv7 (`uuidv7()` in PG 18+, or generated by the app) when ids are created outside the database or shown publicly; remember that v7 reveals the creation time.
8. Never reuse ids, never update primary keys, never expect sequences to be gapless.
9. Use `timestamptz` for instants, `numeric` or integer minor units for money, and `text` + `CHECK` for bounded strings.
10. Prefer a `CHECK` list or a lookup table over an enum when the list of values will change.
11. Use lowercase `snake_case`, plural table names, `id` / `<thing>_id` keys, `*_at` timestamps, `is_`/`has_` booleans, and explicit constraint names.
12. Never store lists in a string, never repeat columns (`tag1`, `tag2`), never point at "any table" with a `(type, id)` pair that has no foreign key.
13. Model trees with `parent_id` + a recursive CTE by default; use `ltree` or a closure table when subtree reads dominate.
14. Use real columns for known attributes and `jsonb` for the long tail; never build EAV (entity-attribute-value) tables.
15. Prefer hard delete plus an archive table; if you soft delete, use partial unique indexes and a view of live rows, and still purge personal data.
16. Write history (audit rows, events, outbox messages) in the same transaction as the change, never in a separate best-effort call.
17. Build job queues with `FOR UPDATE SKIP LOCKED`, a partial index on runnable jobs, a lease timeout, and fast cleanup of finished jobs.
18. Make every consumer idempotent: at-least-once delivery is the normal case.
19. Avoid hot rows: shard counters, aggregate later, or use estimates.
20. For multi-tenant SaaS, start with shared tables and `tenant_id` on every tenant-owned table, first in keys, indexes, and composite foreign keys; add RLS as a safety net.
21. Partition only very large tables, by the column your queries filter on and your retention deletes by; every primary key and unique constraint must include the partition key.
22. Document the schema inside the database with `COMMENT ON`, and review each new table with the checklist in section 10.

## 1. Design process

### 1.1 Start from the domain, not from the screens

**Why.** A schema lives longer than the code that uses it. Tables copied from one screen or one API payload break when the second screen arrives. Tables built from the domain (the real things and rules of the business) stay stable.

**How.** Write five short lists before any DDL (DDL = data definition language: `CREATE`, `ALTER`, `DROP`).

| List | Question | Example (online shop) |
|---|---|---|
| Entities | Which things exist and have an identity? | user, product, order, order line, payment |
| Relationships | How many X per Y? Required or optional? | an order has 1..n lines; a line belongs to exactly 1 order |
| Invariants | What must always be true? | quantity > 0; one active cart per user; a room is never double-booked |
| Access patterns | Which reads and writes matter most, and how often? | "a user's orders, newest first, 20 per page" |
| Lifecycle | How does data grow, change, and leave? | orders kept 10 years; carts deleted after 30 days |

Then:

1. Draw entities and relationships as an ER diagram (entity-relationship diagram, see section 10).
2. Turn each entity into a table, and each relationship into a foreign key or a join table.
3. Turn each invariant into a constraint (section 5). If it cannot be a constraint, write down where it is enforced (a trigger, or a transaction with a lock, see [08](08-transactions-concurrency-locking.md)).
4. For each access pattern, name the index that serves it ([05](05-indexing.md)) and the query shape ([04](04-query-patterns-and-antipatterns.md)).
5. Check the lifecycle: retention and deletion decide soft delete (8.6), archives, and partitioning (8.13).

### 1.2 From invariants to constraints

| Invariant | PostgreSQL mechanism |
|---|---|
| Every order belongs to an existing user | `FOREIGN KEY (user_id) REFERENCES users (id)` |
| Email is unique, ignoring case | unique index on `lower(email)` |
| Quantity is positive | `CHECK (quantity > 0)` |
| A room is never booked twice at the same time | `EXCLUDE USING gist (room_id WITH =, during WITH &&)` |
| One active subscription per user | partial unique index `... WHERE status = 'active'` |
| Order total equals the sum of its lines | not a constraint: compute it, or maintain it in the same transaction |

### 1.3 Normalize first, denormalize with evidence

**Why.** A normalized schema stores each fact once. An update touches one row, and the data cannot contradict itself. Denormalization (storing a fact twice) trades extra writes and a risk of inconsistency for faster reads. Make that trade only when a measured slow query needs it ([06](06-query-optimization-and-explain.md)), and only after indexes and query rewrites were tried.

## 2. Normalization

Two words first:

- **Functional dependency** `A → B`: if you know A, there is exactly one B. Example: `user_id → email`.
- **Anomalies**: an *update anomaly* (you change a fact in one place, an old copy stays elsewhere), an *insert anomaly* (you cannot store X without inventing Y), a *delete anomaly* (deleting Y also loses X). Normal forms remove these anomalies.

### 2.1 First normal form (1NF): one value per cell, no repeating groups

Rule: each column holds one value, there are no repeating groups such as `phone1, phone2`, and each row has a key [30].

```sql
-- Bad: a list inside a string, and repeated columns
CREATE TABLE contacts (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name    text NOT NULL,
    phones  text,              -- '0601020304,0611223344'
    email1  text,
    email2  text
);

-- Good: one row per phone number
CREATE TABLE contacts (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name  text NOT NULL
);

CREATE TABLE contact_phones (
    contact_id  bigint NOT NULL REFERENCES contacts (id) ON DELETE CASCADE,
    phone       text   NOT NULL,
    kind        text   NOT NULL DEFAULT 'mobile' CHECK (kind IN ('mobile', 'home', 'work')),
    PRIMARY KEY (contact_id, phone)
);
```

"One value" depends on use. A `tstzrange`, an address shown as one block, or a small array of labels you never search may be fine. The test: do you need to search, constrain, or join on the parts? If yes, the parts need their own rows or columns.

### 2.2 Second normal form (2NF): no dependency on part of a composite key

Rule: 1NF, and every non-key column depends on the *whole* key.

```sql
-- Bad: product_name depends on product_id only, not on (order_id, product_id)
CREATE TABLE order_lines (
    order_id      bigint  NOT NULL,
    product_id    bigint  NOT NULL,
    product_name  text    NOT NULL,   -- copied into every order; a rename leaves old copies
    quantity      integer NOT NULL,
    PRIMARY KEY (order_id, product_id)
);

-- Good: product facts live in products
CREATE TABLE order_lines (
    order_id    bigint        NOT NULL REFERENCES orders (id) ON DELETE CASCADE,
    product_id  bigint        NOT NULL REFERENCES products (id),
    quantity    integer       NOT NULL CHECK (quantity > 0),
    unit_price  numeric(12,2) NOT NULL CHECK (unit_price >= 0),  -- price paid: a different fact
    PRIMARY KEY (order_id, product_id)
);
```

`unit_price` is **not** a 2NF violation. The current list price lives in `products`; the price *paid* is a historical fact of this order line. Copy values that must not change when the source changes later: prices, tax rates, billing addresses on invoices.

### 2.3 Third normal form (3NF): no dependency through another non-key column

Rule: 2NF, and non-key columns depend only on the key, not on another non-key column (no *transitive* dependency).

```sql
-- Bad: customer_email depends on customer_id, not on the order (id → customer_id → customer_email)
CREATE TABLE orders (
    id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id     bigint      NOT NULL,
    customer_email  text        NOT NULL,
    placed_at       timestamptz NOT NULL
);

-- Good
CREATE TABLE orders (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id  bigint      NOT NULL REFERENCES customers (id),
    placed_at    timestamptz NOT NULL
);
```

Memory aid for 1NF–3NF: every non-key column depends on "the key, the whole key, and nothing but the key".

### 2.4 Boyce–Codd normal form (BCNF)

Rule: for every functional dependency `X → Y`, X is a superkey (a set of columns that is unique) [31]. A 3NF table can still break BCNF when it has overlapping candidate keys.

Example: each teacher teaches exactly one subject, and a student has one teacher per subject.

```sql
-- 3NF but not BCNF: teacher_id → subject, but teacher_id is not a key.
-- Anomaly: teacher 7 can appear with 'math' in one row and 'physics' in another.
CREATE TABLE enrollments (
    student_id  bigint NOT NULL,
    subject     text   NOT NULL,
    teacher_id  bigint NOT NULL,
    PRIMARY KEY (student_id, subject)
);
```

The textbook BCNF fix stores each teacher's subject once, in `teachers (id, subject)`, and keeps only `(student_id, teacher_id)` in `enrollments`. But then the rule "one teacher per subject per student" is lost. A practical middle way keeps the redundant column and lets the database guard it with a **composite foreign key**:

```sql
CREATE TABLE teachers (
    id       bigint PRIMARY KEY,
    subject  text   NOT NULL,
    CONSTRAINT teachers_id_subject_key UNIQUE (id, subject)
);
CREATE TABLE enrollments (
    student_id  bigint NOT NULL,
    subject     text   NOT NULL,
    teacher_id  bigint NOT NULL,
    PRIMARY KEY (student_id, subject),
    FOREIGN KEY (teacher_id, subject) REFERENCES teachers (id, subject)
);
```

The same trick (copy a column, then tie it with a composite foreign key) protects subtypes (8.4) and tenants (8.12).

### 2.5 Fourth and fifth normal forms (rare)

- **4NF** removes independent multi-valued facts stored in one table. Example: `restaurant_offers(restaurant_id, pizza, delivery_area)`: pizzas and delivery areas do not depend on each other, so each pizza repeats for each area. Split into `restaurant_pizzas` and `restaurant_delivery_areas` [32].
- **5NF** handles join dependencies (a table that can only be rebuilt by joining three or more of its projections). You rarely meet it in application schemas.
- Some sources, including Microsoft's archived normalization article, wrongly say that 4NF "is also called BCNF" [30]; they are different forms [31][32].

### 2.6 When and how to denormalize

| Technique | Kept correct by | Cost | Use when |
|---|---|---|---|
| Generated column (`STORED`) | PostgreSQL, on every write | storage; only immutable expressions over the same row | a derived value from the same row that you filter or index |
| Expression index | PostgreSQL | index maintenance | you only search by the derived value |
| Trigger-maintained column | trigger, same transaction | slower writes, hot rows (8.11), hidden logic | a value derived from other rows (`comments_count`) |
| Summary table, same transaction | app or trigger | contention on summary rows | exact aggregates read very often |
| Summary table, rebuilt by a job | scheduled job | stale between runs | dashboards and reports |
| Materialized view | `REFRESH MATERIALIZED VIEW [CONCURRENTLY]` | full recompute on each refresh | expensive queries that may be a bit stale |
| Snapshot of a fact | never updated | none: it is a different fact | price, tax, address at the time of an event |

Generated column. Always write `STORED` or `VIRTUAL` explicitly: before PG 18 only `STORED` exists and is required; from PG 18 the default is `VIRTUAL` [2][27]. In PG 18 a virtual column cannot be indexed or used in a primary key, unique, or foreign key constraint (the source code raises errors such as "indexes on virtual generated columns are not supported") [28][95]. Use `STORED` or an expression index when you need an index.

```sql
CREATE TABLE users (
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email         text NOT NULL,
    email_domain  text GENERATED ALWAYS AS (lower(split_part(email, '@', 2))) STORED
);
CREATE INDEX users_email_domain_idx ON users (email_domain);
```

Trigger-maintained column (for example `posts.comments_count`): an `AFTER INSERT OR DELETE` trigger on `comments` runs `UPDATE posts SET comments_count = comments_count ± 1`. It is exact, but every new comment locks the post row until commit, so popular posts become hot rows (8.11). Trigger syntax is shown in 7.2 and 8.7.1.

Materialized view. `REFRESH ... CONCURRENTLY` keeps readers unblocked but needs a unique index on plain columns that covers all rows, and works only on a populated view [29].

```sql
CREATE MATERIALIZED VIEW daily_revenue AS
SELECT (placed_at AT TIME ZONE 'UTC')::date AS day,
       sum(total)                           AS revenue,
       count(*)                             AS orders
FROM orders
GROUP BY 1;

CREATE UNIQUE INDEX daily_revenue_day_key ON daily_revenue (day);

REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue;
```

The fixed `'UTC'` matters: `date_trunc('day', placed_at)` would depend on the session time zone of whoever refreshes the view.

## 3. Keys and identifiers

### 3.1 Natural keys vs surrogate keys

- A **natural key** comes from the domain and is unique: an email, an ISO country code, an ISBN.
- A **surrogate key** has no business meaning and is generated by the system: an identity number or a UUID.

| | Natural key | Surrogate key |
|---|---|---|
| Stability | can change (emails change, product codes get renamed) | never changes |
| Size | often wide text, copied into every foreign key | 8 or 16 bytes |
| Readability | readable in joins and logs | needs a join to read |
| Good for | small, stable code lists (`currency_code`) and join tables | almost every entity table |

Rule: give entity tables a surrogate primary key, **and** keep a `UNIQUE` constraint on the natural key: you still need the uniqueness.

```sql
CREATE TABLE users (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email       text        NOT NULL,
    created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX users_email_lower_key ON users (lower(email));

-- Stable code list: the natural key is the primary key
CREATE TABLE currencies (
    code        text     PRIMARY KEY CHECK (code ~ '^[A-Z]{3}$'),  -- ISO 4217
    minor_unit  smallint NOT NULL CHECK (minor_unit BETWEEN 0 AND 4)
);
```

### 3.2 Choosing the primary key type

| Option | Size | Insert locality in the index | Generated by | Reveals | Use when |
|---|---|---|---|---|---|
| `bigint GENERATED ALWAYS AS IDENTITY` | 8 B | excellent (always appends at the end) | database | row count, creation order | default for internal tables |
| `integer` identity | 4 B | excellent | database | same | small lookup tables only (max 2,147,483,647) |
| UUIDv7 | 16 B | good (time-ordered) | database (`uuidv7()`, PG 18+) or app | creation time to the millisecond [9] | ids created by clients or other services, merged data, public ids |
| UUIDv4 (`gen_random_uuid()`) | 16 B | poor (random positions) | database or app | nothing | public tokens, small tables; avoid as key of big write-heavy tables |
| ids stored as `text` (ULID, nanoid, `ord_...`) | 20–40 B | depends | app | depends | avoid as storage format: store a `uuid`, format it at the API edge |

Store 128-bit ids in the `uuid` type (16 bytes), never as `text` (36 characters plus a header).

### 3.3 `bigint` identity: the default

```sql
CREATE TABLE orders (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id    bigint      NOT NULL REFERENCES users (id),
    placed_at  timestamptz NOT NULL DEFAULT now()
);
```

- `GENERATED ALWAYS` rejects a manual id unless the `INSERT` says `OVERRIDING SYSTEM VALUE`; it protects against accidental explicit ids. `BY DEFAULT` lets an explicit value win, which helps data imports [1][12].
- Do not use `serial`: it is a legacy shortcut with "weird behaviors" for permissions and dependencies [4].
- Do not use `integer` for tables that can grow. Changing `integer` to `bigint` later rewrites the whole table (see [10](10-safe-schema-migrations.md)).
- An identity column does not guarantee uniqueness by itself; the `PRIMARY KEY` does [12].
- Gaps are normal. Rolled-back transactions and `INSERT ... ON CONFLICT` consume values; sequences "cannot be used to obtain gapless sequences" [11]. For legally gapless numbers (invoice numbers), use a counter row updated in the same transaction ([08](08-transactions-concurrency-locking.md)).
- Partitioned tables accept identity columns from PG 17 [13]. On PG 14–16, use a sequence default or a UUID on partitioned tables.

### 3.4 UUIDs: random v4 vs time-ordered v7

**Why random UUIDs hurt.** A B-tree index keeps keys sorted. Random keys land on random index pages, so the whole index must stay in memory, pages split everywhere, and the first change to each page after a checkpoint writes a full-page image to the WAL (write-ahead log, the change log used for crash recovery and replication). Tomas Vondra measured over 20 GB of WAL with random UUIDs versus 2.5 GB with a time-based generator in the same insert test, and random-UUID throughput fell below 30% once the data no longer fit in shared buffers [6]. Ants Aasma measured an index-only scan over 10 million rows: 27,332 buffer hits for `bigint`, 39,126 for UUIDv7, and 8,562,960 for UUIDv4 [7].

**UUIDv7** puts a 48-bit Unix timestamp in milliseconds at the front [9], so new values arrive near the end of the index, like a sequence.

```sql
-- PG 18+
CREATE TABLE documents (
    id          uuid PRIMARY KEY DEFAULT uuidv7(),
    title       text        NOT NULL,
    created_at  timestamptz NOT NULL DEFAULT now()
);

SELECT id, uuid_extract_timestamp(id) AS id_time  -- uuid_extract_timestamp(): PG 17+
FROM documents
ORDER BY id DESC
LIMIT 5;
```

- PG 18 adds `uuidv7()` and the alias `uuidv4()`; `gen_random_uuid()` returns v4 in all supported versions [2][5].
- On PG 14–17, generate v7 in the application, for example with `import { v7 as uuidv7 } from 'uuid'` [94].
- UUIDv7 reveals the creation time to anyone who sees the id. RFC 9562 says to use UUIDv4 when ids are involved in security operations [9].
- Never treat any UUID as a secret: RFC 9562 says UUIDs "MUST NOT be used as security capabilities" [9].
- App-generated v7 ids from several servers are only roughly ordered (clock differences). That is fine for index locality; do not use the id as an exact event order.

### 3.5 Public identifiers vs internal ids

Sequential ids in URLs reveal your volume (orders per day) and invite enumeration (trying `id=1, 2, 3...`) [8]. Random ids are only defense in depth: every access still needs an authorization check [10]. Options:

1. Internal `bigint` key plus a public `uuid` column used in URLs and APIs.
2. UUIDv7 as the only key, everywhere (simpler: one id per row).
3. A readable prefix added at the API layer (`ord_...`, Stripe style), while the database stores the raw value [8].

```sql
CREATE TABLE invoices (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    public_id  uuid   NOT NULL DEFAULT gen_random_uuid(),
    user_id    bigint NOT NULL REFERENCES users (id),
    CONSTRAINT invoices_public_id_key UNIQUE (public_id)
);
```

### 3.6 Composite keys for join tables

```sql
CREATE TABLE post_tags (
    post_id  bigint NOT NULL REFERENCES posts (id) ON DELETE CASCADE,
    tag_id   bigint NOT NULL REFERENCES tags (id)  ON DELETE CASCADE,
    PRIMARY KEY (post_id, tag_id)
);
-- The primary key serves "tags of a post"; this index serves "posts with a tag"
-- and the foreign key check when a tag is deleted.
CREATE INDEX post_tags_tag_id_post_id_idx ON post_tags (tag_id, post_id);
```

The composite key blocks duplicate pairs for free. Add a surrogate `id` only when the pair is referenced by other tables, and then keep `UNIQUE (post_id, tag_id)`. Karwin calls the habit of adding an `id` to every table, even join tables, the "ID Required" anti-pattern [46].

### 3.7 Never reuse or change ids

- A deleted id must never come back: caches, logs, URLs, and other systems still point at it.
- Do not update primary keys. `ON UPDATE CASCADE` rewrites many rows, and external references break. If a "key" can change, it is not a good primary key: use a surrogate.
- Do not encode meaning in ids (region, year): meanings change.

### 3.8 Prisma notes on ids

- `@default(uuid())`, `@default(uuid(7))` and `cuid()` are generated by Prisma Client and are "not visible in the database schema" [35]: the migration has no `DEFAULT`, so raw SQL inserts (psql, node-postgres, other services) must provide the id. On PG 18 you can let the database do it: `@default(dbgenerated("uuidv7()")) @db.Uuid`.
- More in [15](15-postgres-from-typescript.md).

## 4. Type choices in modeling

This section covers the *modeling* decision only. Type details are in [03](03-postgresql-features-and-types.md).

| You need | Use | Avoid |
|---|---|---|
| A moment in time | `timestamptz` | `timestamp` (no time zone) [4] |
| A calendar date (birthday, due date) | `date` | `timestamptz` at midnight |
| Money | `numeric(p,s)`, or `bigint` minor units + a currency code | `money`, `real`, `double precision` [4] |
| A bounded string | `text` + `CHECK (char_length(col) <= n)` | `char(n)`; `varchar(n)` by reflex [4][20] |
| Yes/no | `boolean NOT NULL DEFAULT false` | several booleans that encode one state |
| When something happened | `timestamptz` (`verified_at`) | a boolean (`is_verified`) when the time matters |
| A fixed set of values | `CHECK`, enum, or lookup table (4.2) | free text |
| A reusable rule on a type | a domain (4.3) | copying the same `CHECK` everywhere |
| An interval of time | `tstzrange` / `daterange` + `EXCLUDE` | two columns without a constraint |
| Flexible attributes | `jsonb` with a `CHECK` on its shape (4.4) | EAV tables (8.5) |
| A short list read with its row | an array (4.5) | a comma-separated string |

`text` and `varchar(n)` perform the same in PostgreSQL; the only cost is "a few extra CPU cycles to check the length" [20]. A `CHECK` is easier to change later than a `varchar(n)`.

### 4.1 Booleans vs status columns vs timestamps

```sql
-- Bad: flags that can contradict each other (draft AND archived?)
CREATE TABLE posts (
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    is_draft      boolean,
    is_published  boolean,
    is_archived   boolean
);

-- Good: one status, plus the time of the transitions you care about
CREATE TABLE posts (
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    status        text NOT NULL DEFAULT 'draft'
                  CHECK (status IN ('draft', 'published', 'archived')),
    published_at  timestamptz,
    CONSTRAINT posts_published_at_check
        CHECK (status <> 'published' OR published_at IS NOT NULL)
);
```

A single boolean is fine when there are truly two states (`is_admin`). A nullable timestamp (`verified_at`, `cancelled_at`) gives both the flag and the time.

### 4.2 Enum vs lookup table vs `CHECK`

Three alternatives for the same column (pick one):

```sql
-- Option A: CHECK list
CREATE TABLE orders (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    status  text NOT NULL DEFAULT 'pending'
            CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled'))
);

-- Option B: enum type
CREATE TYPE order_status AS ENUM ('pending', 'paid', 'shipped', 'cancelled');
ALTER TYPE order_status ADD VALUE 'refunded' AFTER 'shipped';
ALTER TYPE order_status RENAME VALUE 'cancelled' TO 'canceled';

-- Option C: lookup table with a readable text key (no join needed to read the code)
CREATE TABLE order_statuses (
    code        text     PRIMARY KEY,
    label       text     NOT NULL,
    sort_order  smallint NOT NULL,
    is_final    boolean  NOT NULL DEFAULT false
);
-- in orders:  status text NOT NULL DEFAULT 'pending' REFERENCES order_statuses (code)
```

| Need | `CHECK (col IN (...))` | Enum type | Lookup table + FK |
|---|---|---|---|
| Add a value | replace the constraint (`NOT VALID` + `VALIDATE`, see [10](10-safe-schema-migrations.md)) | `ALTER TYPE ... ADD VALUE` | `INSERT` a row |
| Remove a value | replace the constraint | impossible without recreating the type [17] | `DELETE` (the FK blocks it if still used) |
| Rename a value | update rows, replace the constraint | `ALTER TYPE ... RENAME VALUE` [18] | update the row (`ON UPDATE CASCADE` with a text key) |
| Extra data (label, order, active flag) | no | no | yes |
| Storage per row | the text itself | 4 bytes [17] | the key column |
| Sort order | alphabetical | declaration order | your `sort_order` column |
| Best for | short, stable lists used in one table | stable lists shared by many tables, where order matters | lists that change, are managed by users, or carry data |

Enum gotcha: a value added inside a transaction block "cannot be used until after the transaction has been committed" [18]. Migration tools that wrap a whole migration in one transaction hit this.

### 4.3 Domains

A domain is a named type with constraints, reusable across tables.

```sql
CREATE DOMAIN currency_code AS text CHECK (VALUE ~ '^[A-Z]{3}$');
CREATE DOMAIN non_negative_amount AS numeric(14,2) CHECK (VALUE >= 0);

CREATE TABLE prices (
    product_id  bigint              NOT NULL REFERENCES products (id),
    currency    currency_code       NOT NULL,
    amount      non_negative_amount NOT NULL,
    PRIMARY KEY (product_id, currency)
);
```

Put `NOT NULL` on the column, not on the domain: a domain column can still read as NULL (outer joins, empty subqueries), so the docs recommend allowing NULL in the domain and adding `NOT NULL` per column [19].

### 4.4 `jsonb` or real columns?

- Use **real columns** for anything you filter, join, sort, constrain, or aggregate often.
- Use **`jsonb`** for the long tail of optional attributes, data stored and returned as a whole (webhook payloads, settings), and per-tenant custom fields.
- `jsonb` repeats key names in every row: Heap measured 164 MB versus 79 MB for the same data in columns [25].
- The planner keeps no per-key statistics inside `jsonb`; Heap saw it fall back to a fixed guess of 0.1% selectivity, which produced very bad plans [25]. An expression index, or `CREATE STATISTICS` on an expression (PG 14+) [15], gives the planner real numbers for a hot key.
- Any update rewrites and locks the whole row; the docs advise keeping JSON documents to "a manageable size" and giving them "a somewhat fixed structure" [23].
- Guard the shape: `CHECK (jsonb_typeof(attributes) = 'object')` in every version, or `CHECK (attributes IS JSON OBJECT)` (PG 16+) [16].

### 4.5 Arrays

Arrays are fine for a small, bounded list read together with its row (labels shown on a card), with a GIN index for `@>` searches. When elements need foreign keys, attributes, or individual updates, use a join table. The docs say it directly: "Arrays are not sets; searching for specific array elements can be a sign of database misdesign" [24].

### 4.6 Prisma type mapping notes

- Prisma `DateTime` maps to `timestamp(3)` (without time zone) by default; add `@db.Timestamptz(3)` [36].
- Prisma `Decimal` maps to `decimal(65,30)` by default; set the precision you need, for example `@db.Decimal(12, 2)` [36].
- Prisma model and field names become quoted mixed-case identifiers unless you map them (6.1).

## 5. Constraints: the last line of defense

**Why.** The app is not the only writer: scripts, migrations, admin tools, other services, and AI agents all write SQL. App-side checks also race: two requests can both "check that the email is free" and both insert. A `UNIQUE` constraint cannot be raced; see [08](08-transactions-concurrency-locking.md) for why.

### 5.1 `NOT NULL` by default

- Fewer three-valued-logic surprises (7.1). A `NOT NULL` constraint is also cheaper than the equivalent `CHECK (col IS NOT NULL)` [3].
- PG 18 stores `NOT NULL` constraints in `pg_constraint`, so they can have names, and `ALTER TABLE` can add them as `NOT VALID` [2]. This helps on big tables ([10](10-safe-schema-migrations.md)).

### 5.2 `CHECK`

```sql
CREATE TABLE bookings (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room_id    bigint      NOT NULL REFERENCES rooms (id),
    starts_at  timestamptz NOT NULL,
    ends_at    timestamptz NOT NULL,
    guests     smallint    NOT NULL,
    note       text,
    CONSTRAINT bookings_time_order_check  CHECK (ends_at > starts_at),
    CONSTRAINT bookings_guests_check      CHECK (guests BETWEEN 1 AND 20),
    CONSTRAINT bookings_note_length_check CHECK (char_length(note) <= 2000)
);
```

- A `CHECK` passes when its expression is NULL, so a NULL `note` is accepted.
- A `CHECK` sees only the current row. PostgreSQL "does not support CHECK constraints that reference table data other than the new or updated row"; such a check may seem to work in tests and then break dump and restore [3]. For rules across rows or tables, use a foreign key, an exclusion constraint, or a trigger.

### 5.3 `UNIQUE`

```sql
-- Composite: an email is unique inside a tenant
ALTER TABLE users ADD CONSTRAINT users_tenant_email_key UNIQUE (tenant_id, email);

-- Partial: one default address per user
CREATE UNIQUE INDEX addresses_one_default_per_user_key
    ON addresses (user_id) WHERE is_default;

-- Expression: unique ignoring case
CREATE UNIQUE INDEX users_email_lower_key ON users (lower(email));

-- NULL treated as a value (PG 15+): one redemption per (user, coupon), even without a coupon
ALTER TABLE redemptions
    ADD CONSTRAINT redemptions_user_coupon_key UNIQUE NULLS NOT DISTINCT (user_id, coupon_code);
```

By default two NULLs are *not* equal for uniqueness, so a unique constraint allows many rows with NULL in a constrained column; `NULLS NOT DISTINCT` (PG 15+) changes that [3][14]. Partial unique indexes are described in the docs as "Setting up a Partial Unique Index" [55].

### 5.4 Foreign keys and `ON DELETE`

| Action | When the parent row is deleted | Use for |
|---|---|---|
| `NO ACTION` (default) | error at the end of the statement, or at commit if the constraint is deferred | most references |
| `RESTRICT` | error at once; cannot be deferred [3] | "never delete a parent that still has children" |
| `CASCADE` | children are deleted too | children *owned* by the parent: order lines of an order |
| `SET NULL` | foreign key columns become NULL | optional links: `posts.author_id` when a user leaves |
| `SET NULL (col, ...)` (PG 15+) | only the listed columns become NULL [14] | composite keys that include `tenant_id` |
| `SET DEFAULT` | columns get their default | rare |

- **Index the referencing columns.** PostgreSQL does not do it for you. Without the index, every delete or key update on the parent scans the child table [3].
- Use `CASCADE` only for ownership. Deleting a user should not silently delete invoices: use `RESTRICT` and an explicit process. A cascade can delete millions of rows in one statement.
- The docs show a tenant-aware composite key with `ON DELETE SET NULL (author_id)`: without the column list, the delete would also set `tenant_id` to NULL, which the primary key forbids [3]. See 8.12.

### 5.5 `EXCLUDE`: no overlapping bookings

An exclusion constraint guarantees that no two rows "match" with the given operators. With `&&` (overlaps) it forbids overlapping ranges.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;  -- lets GiST compare plain bigint with =

CREATE TABLE room_bookings (
    id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room_id  bigint    NOT NULL REFERENCES rooms (id),
    during   tstzrange NOT NULL,
    status   text      NOT NULL DEFAULT 'confirmed' CHECK (status IN ('confirmed', 'cancelled')),
    CONSTRAINT room_bookings_no_overlap_excl
        EXCLUDE USING gist (room_id WITH =, during WITH &&) WHERE (status = 'confirmed')
);

INSERT INTO room_bookings (room_id, during)
VALUES (1, tstzrange('2026-11-02 10:00+01', '2026-11-02 11:00+01'));  -- '[)' bounds by default
INSERT INTO room_bookings (room_id, during)
VALUES (1, tstzrange('2026-11-02 11:00+01', '2026-11-02 12:00+01'));  -- OK: touches, no overlap
```

- Range constructors default to `[)` (lower bound included, upper excluded), so back-to-back bookings do not overlap [85].
- A violation raises SQLSTATE `23P01` (`exclusion_violation`) [92].
- The predicate needs parentheses, and GIN cannot be used; in practice exclusion constraints use GiST or SP-GiST [1].
- On partitioned tables, exclusion constraints work from PG 17 if they compare the partition key columns with equality [13].
- PG 18 offers temporal keys as an alternative: `PRIMARY KEY (room_id, during WITHOUT OVERLAPS)` (8.7.4). It does not accept a `WHERE` predicate, and empty ranges are not allowed [1].

### 5.6 Deferrable constraints

**Why.** Some valid changes pass through an invalid state in the middle of a transaction: swapping two positions, inserting two rows that reference each other, or loading data in any order.

```sql
CREATE TABLE playlist_items (
    playlist_id  bigint  NOT NULL REFERENCES playlists (id) ON DELETE CASCADE,
    position     integer NOT NULL,
    song_id      bigint  NOT NULL REFERENCES songs (id),
    CONSTRAINT playlist_items_position_key
        UNIQUE (playlist_id, position) DEFERRABLE INITIALLY IMMEDIATE
);

BEGIN;
SET CONSTRAINTS playlist_items_position_key DEFERRED;
UPDATE playlist_items SET position = 2 WHERE playlist_id = 1 AND song_id = 10;
UPDATE playlist_items SET position = 1 WHERE playlist_id = 1 AND song_id = 20;
COMMIT;  -- uniqueness is checked here
```

- Only `UNIQUE`, `PRIMARY KEY`, `EXCLUDE`, and foreign keys can be deferrable; `NOT NULL` and `CHECK` cannot [1].
- A deferrable constraint cannot be the arbiter of `INSERT ... ON CONFLICT` [1].
- PostgreSQL checks a *non-deferrable* unique constraint row by row, so even a single `UPDATE` that swaps two values can fail. `DEFERRABLE INITIALLY IMMEDIATE` gives the SQL-standard end-of-statement check, but "can be significantly slower" [1].
- Section 8.14 shows a circular foreign key (`documents` ↔ `document_versions`) made `DEFERRABLE INITIALLY DEFERRED`.

### 5.7 Adding constraints to existing tables, and `NOT ENFORCED`

- On big tables, add `CHECK` and foreign keys as `NOT VALID`, then `VALIDATE CONSTRAINT` in a second step; validation takes only a `SHARE UPDATE EXCLUSIVE` lock [83]. Details and the full playbook are in [10](10-safe-schema-migrations.md).
- PG 18 adds `NOT ENFORCED` for `CHECK` and foreign keys: the database records the constraint but does not check it; it is "useful as documentation if the actual checking ... is too expensive" [1][2]. Use it rarely: the data will drift.
- PG 19 adds `ALTER TABLE ... ALTER CONSTRAINT ... [NOT] ENFORCED` for `CHECK` constraints (PG 19, beta — may change) [59].

### 5.8 Name constraints, and validate in both places

- Name every constraint (`CONSTRAINT orders_total_check CHECK (...)`). The name appears in error messages, so the app can map it to a user message, and migrations can refer to it.
- Validate in the app for user experience (fast feedback, friendly text); validate in the database for truth.
- Map SQLSTATE codes to app errors [92]:

| SQLSTATE | Condition | Typical user message |
|---|---|---|
| `23505` | `unique_violation` | "This email is already used." |
| `23503` | `foreign_key_violation` | "The referenced item does not exist (or is still in use)." |
| `23514` | `check_violation` | "Value out of range." |
| `23502` | `not_null_violation` | "This field is required." |
| `23P01` | `exclusion_violation` | "This slot is already booked." |

With node-postgres, the error object carries `code` and `constraint`; Prisma wraps them in its own error codes. See [15](15-postgres-from-typescript.md).

## 6. Naming conventions

### 6.1 Lowercase `snake_case`, never quoted mixed case

PostgreSQL folds unquoted names to lowercase. A table created as `"User"` (with quotes) must be quoted *forever*: `SELECT "createdAt" FROM "User"`. The wiki says: don't use upper case table or column names [4]. Prisma creates exactly such names (`"User"`, `"createdAt"`) unless you map them [35]:

```prisma
model User {
  id        String   @id @default(dbgenerated("uuidv7()")) @db.Uuid   // PG 18+
  createdAt DateTime @default(now()) @map("created_at") @db.Timestamptz(3)

  @@map("users")
}
```

### 6.2 Singular or plural table names

| Camp | Arguments |
|---|---|
| Plural or collective (`users`, `order_lines`) | a table is a set of rows; reads like English (`FROM users`); avoids reserved words: `USER` is reserved, `ORDER` and `GROUP` are reserved in PostgreSQL [33]; the SQL Style Guide says "use a collective name or, less ideally, a plural form" [34]; Rails and GitLab use plural |
| Singular (`user`, `order_line`) | a row is one entity; matches class and ORM model names (Prisma models are singular [35]); no irregular plurals (`person`/`people`) |

**Recommendation for this library:** plural table names, singular column names. The deciding argument in PostgreSQL is practical: `user`, `order`, and `group` are reserved words, so singular names force quoting or awkward renames. In an existing project, follow its convention: consistency beats either choice.

### 6.3 Patterns

| Object | Pattern | Example |
|---|---|---|
| Table | plural `snake_case` noun | `users`, `order_lines` |
| Join table | both names, or a domain noun if it carries data | `post_tags`, `memberships` |
| Primary key column | `id` | `id` |
| Foreign key column | `<singular referenced table>_id`, or a role name + `_id` | `user_id`, `author_id`, `reviewer_id` |
| Instant | past participle + `_at` | `created_at`, `paid_at`, `deleted_at` |
| Calendar date | `_on` or `_date` | `due_on`, `birth_date` |
| Boolean | `is_` / `has_` / `can_` | `is_active`, `has_attachments` |
| Quantity with a unit | name + unit | `amount_minor`, `duration_ms`, `size_bytes` |
| Primary key constraint | `<table>_pkey` | `orders_pkey` |
| Unique constraint | `<table>_<columns>_key` | `users_email_key` |
| Foreign key constraint | `<table>_<columns>_fkey` | `orders_user_id_fkey` |
| Check constraint | `<table>_<columns or purpose>_check` | `bookings_time_order_check` |
| Exclusion constraint | `<table>_<columns or purpose>_excl` | `room_bookings_no_overlap_excl` |
| Index | `<table>_<columns>_idx` | `orders_user_id_placed_at_idx` |
| Partial or special index | add the purpose | `jobs_runnable_idx`, `users_email_lower_key` |

These suffixes are the ones PostgreSQL uses when it names objects itself: `_pkey`, `_key`, `_fkey`, `_check`, `_excl`, `_idx`, and, for named `NOT NULL` constraints in PG 18, `_not_null` [38] (cross-checked in the PG 18 source [28][95][96]). GitLab uses prefixes instead (`fk_`, `index_`, `check_`) [37]. Both work; pick one per project.

Other rules:

- Names are limited to 63 bytes; longer names are silently truncated [37].
- No `tbl_` prefixes or Hungarian notation [34]. No spaces, no names that differ only by case.
- Avoid SQL keywords, even non-reserved ones that read badly (`type`, `value`, `key`). Prefer `kind`, `amount`, `api_key`.
- A unit in the name prevents bugs: `timeout_ms` cannot be confused with seconds.
- The SQL Style Guide advises against a bare `id` as the primary identifier [34]; most ORMs expect `id`. This library uses `id`.

## 7. NULLs, timestamps, and column order

### 7.1 Designing with NULL

- NULL means "unknown" or "does not apply". Give each nullable column one meaning and write it down (`COMMENT ON`, section 10).
- NULL follows three-valued logic: `WHERE status <> 'paid'` skips NULL rows, and `NOT IN (subquery)` returns nothing if the subquery contains a NULL [4] (see [01](01-sql-fundamentals.md) and [04](04-query-patterns-and-antipatterns.md)).
- Do not use magic values instead of NULL: `''`, `0`, `-1`, or `'1970-01-01'` lie to aggregates and constraints.
- Many optional columns that are filled together often belong in a separate 1:1 table (`user_profiles`), which keeps the main table narrow and the columns `NOT NULL`.
- Remember the uniqueness rule for NULLs (5.3).

### 7.2 Timestamps and time zones

- Default: `created_at timestamptz NOT NULL DEFAULT now()`.
- `now()` returns the start time of the current transaction, so every row written in one transaction gets the same value; `clock_timestamp()` returns the real time and changes even within one statement [22].
- `timestamptz` stores an instant in UTC; "the originally stated or assumed time zone is not retained" [21]. If you need the user's zone (to display or to schedule), store it in its own column (`time_zone text`, an IANA name such as `'Europe/Paris'`).
- For future local events (a meeting at 09:00 Paris time next year), store the local date-time plus the zone name, and derive the UTC instant: time zone rules can change before the event [93].
- Keep business time and system time apart: `paid_at` (when the provider says payment happened) is not `created_at` (when your row was inserted).

Who sets `updated_at`?

1. **A trigger** (correct for every writer: ORM, raw SQL, scripts):

```sql
CREATE FUNCTION set_updated_at() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  NEW.updated_at := now();
  RETURN NEW;
END $$;

CREATE TRIGGER orders_set_updated_at
BEFORE UPDATE ON orders
FOR EACH ROW
WHEN (OLD.* IS DISTINCT FROM NEW.*)   -- skip no-op updates
EXECUTE FUNCTION set_updated_at();
```

2. **The application.** Prisma's `@updatedAt` is set by Prisma Client only [35]; raw SQL updates leave it unchanged. Prefer the trigger when anything besides the ORM writes to the table.

### 7.3 Column order and alignment padding ("column tetris")

**Why.** Each fixed-width type has an alignment. PostgreSQL inserts padding bytes so that, for example, a `bigint` starts on an 8-byte boundary. A bad column order wastes space in every row [39][40].

| Type | Size | Alignment (from `pg_type`) |
|---|---|---|
| `bigint`, `timestamptz`, `timestamp`, `double precision` | 8 B | 8 |
| `integer`, `date`, `real` | 4 B | 4 |
| `smallint` | 2 B | 2 |
| `boolean` | 1 B | 1 |
| `uuid` | 16 B | 1 (no padding needed) |
| `text`, `numeric`, `jsonb` | variable | 4 (short values, up to 126 bytes, skip the padding) |

```sql
-- Bad: 1 + 7 (padding) + 8 + 2 + 6 (padding) + 8 + 4 = 36 bytes of data
SELECT pg_column_size(ROW(true, 1::bigint, 1::smallint, now(), 1)) AS bad_order;
-- Good: 8 + 8 + 4 + 2 + 1 = 23 bytes of data
SELECT pg_column_size(ROW(1::bigint, now(), 1, 1::smallint, true)) AS good_order;
-- Expected on 64-bit builds: 60 and 47 (each includes a 24-byte header)
```

**Rule:** for new tables expected to be large, order columns 8-byte types first, then 4, 2, and 1-byte types, then variable-length types; keep `id` first for readability. Shaun Thomas shrank a one-million-row table from 135 MB to 112 MB just by reordering its columns (he reports "21% of the total space" saved) [39]. GitLab requires this ordering for new tables [40].

**When it is not worth it:** small tables, and existing tables. PostgreSQL cannot move a column; you must recreate the table or add columns and move data [41].

## 8. Design patterns

Each pattern gives the problem, a schema, the key queries, the trade-offs, and when to use it.

### 8.1 Hierarchies (trees)

**Problem.** Categories, folders, org charts, and threaded comments form trees. SQL tables are flat, so you must choose how to store parent-child links.

**Adjacency list** (default). Each row stores its parent; recursive CTEs (common table expressions) walk the tree.

```sql
CREATE TABLE categories (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    parent_id  bigint REFERENCES categories (id) ON DELETE RESTRICT,
    name       text NOT NULL,
    CONSTRAINT categories_not_own_parent_check CHECK (parent_id <> id)
);
CREATE INDEX categories_parent_id_idx ON categories (parent_id);

-- Subtree of category 7, depth-first order, protected against accidental cycles (PG 14+)
WITH RECURSIVE subtree AS (
    SELECT id, parent_id, name, 1 AS depth
    FROM categories
    WHERE id = 7
  UNION ALL
    SELECT c.id, c.parent_id, c.name, s.depth + 1
    FROM categories AS c
    JOIN subtree AS s ON c.parent_id = s.id
) SEARCH DEPTH FIRST BY name SET ordercol
  CYCLE id SET is_cycle USING path
SELECT id, name, depth
FROM subtree
WHERE NOT is_cycle
ORDER BY ordercol;
```

For ancestors (a breadcrumb), recurse upward instead: start from the node and join `ON c.id = a.parent_id`. The `SEARCH` and `CYCLE` clauses exist since PG 14 [15][42]. Karwin's "Naive Trees" chapter [46] criticizes adjacency lists because walking a deep tree takes many queries; with `WITH RECURSIVE`, PostgreSQL walks it in one query. Never walk the tree with one query per level from the application.

**Materialized path with `ltree`.** Each row stores the full path from the root (`'1.4.17'`). Subtree and ancestor checks become indexed operators [43].

```sql
CREATE EXTENSION IF NOT EXISTS ltree;

CREATE TABLE categories (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    parent_id  bigint REFERENCES categories (id),   -- keep it: ltree has no referential integrity
    name       text  NOT NULL,
    path       ltree NOT NULL                        -- ids from the root, e.g. '1.4.17'
);
CREATE INDEX categories_path_gist_idx ON categories USING gist (path);

SELECT id, name FROM categories WHERE path <@ '1.4';                          -- subtree of node 4
SELECT id, name FROM categories WHERE path @> '1.4.17' ORDER BY nlevel(path); -- ancestors of 17

-- Move node 4 (path '1.4') under node 9 (path '2.9'): rewrite every path in the subtree
UPDATE categories
SET path = '2.9'::ltree || subpath(path, nlevel('1.4'::ltree) - 1)
WHERE path <@ '1.4';
```

Labels may contain letters, digits, and underscores; PG 16 also allows hyphens and raised the label limit from 256 to 1000 characters [16][43].

**Closure table.** A second table stores every ancestor-descendant pair, including each node with itself at depth 0 [44].

```sql
CREATE TABLE category_paths (
    ancestor_id    bigint   NOT NULL REFERENCES categories (id) ON DELETE CASCADE,
    descendant_id  bigint   NOT NULL REFERENCES categories (id) ON DELETE CASCADE,
    depth          smallint NOT NULL CHECK (depth >= 0),
    PRIMARY KEY (ancestor_id, descendant_id)
);
CREATE INDEX category_paths_descendant_idx ON category_paths (descendant_id, ancestor_id);

-- Insert node 42 under parent 7: copy the parent's ancestor rows, plus the self row
INSERT INTO category_paths (ancestor_id, descendant_id, depth)
SELECT ancestor_id, 42, depth + 1 FROM category_paths WHERE descendant_id = 7
UNION ALL
SELECT 42, 42, 0;

-- Whole subtree of 7 (add "AND p.depth = 1" for direct children only)
SELECT c.*
FROM categories AS c
JOIN category_paths AS p ON p.descendant_id = c.id
WHERE p.ancestor_id = 7;

-- Move the subtree of 42 under 9. Step 1: cut links from outside ancestors into the subtree
DELETE FROM category_paths AS p
USING category_paths AS sub
WHERE sub.ancestor_id = 42
  AND p.descendant_id = sub.descendant_id
  AND NOT EXISTS (SELECT 1 FROM category_paths AS inside
                  WHERE inside.ancestor_id = 42
                    AND inside.descendant_id = p.ancestor_id);
-- Step 2: link every ancestor of 9 (and 9 itself) to every node of the subtree
INSERT INTO category_paths (ancestor_id, descendant_id, depth)
SELECT sup.ancestor_id, sub.descendant_id, sup.depth + sub.depth + 1
FROM category_paths AS sup
CROSS JOIN category_paths AS sub
WHERE sup.descendant_id = 9
  AND sub.ancestor_id = 42;
```

**Nested sets** (`lft`, `rgt` numbers from a depth-first walk, popularized by Joe Celko): a subtree is a range scan, but an insert renumbers a large part of the table [45]. Use only for trees that almost never change.

| Model | Subtree read | Ancestors read | Insert | Move a subtree | Integrity | Use when |
|---|---|---|---|---|---|---|
| Adjacency list | recursive CTE | recursive CTE | 1 row | 1 update | foreign key | default; frequent writes |
| `ltree` path | `<@` with GiST, fast | `@>`, fast | 1 row (compute path) | update all descendants | none on the path (keep `parent_id`) | read-heavy trees, path sorting |
| Closure table | join, fast | join, fast | depth + 1 rows | delete + insert many rows | foreign keys | many subtree/ancestor queries, depth filters |
| Nested sets | range scan | range scan | renumber many rows | renumber | none | static trees |

### 8.2 Many-to-many with attributes

**Problem.** A user belongs to many teams, and each membership has a role and a join date. The relationship itself carries data, so it deserves a real table named after the relationship.

```sql
CREATE TABLE memberships (
    team_id     bigint      NOT NULL REFERENCES teams (id) ON DELETE CASCADE,
    user_id     bigint      NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    role        text        NOT NULL DEFAULT 'member' CHECK (role IN ('owner', 'admin', 'member')),
    invited_by  bigint      REFERENCES users (id) ON DELETE SET NULL,
    joined_at   timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (team_id, user_id)
);
CREATE INDEX memberships_user_id_idx ON memberships (user_id);       -- "teams of a user"
CREATE INDEX memberships_invited_by_idx ON memberships (invited_by);  -- foreign key support
-- At most one owner per team
CREATE UNIQUE INDEX memberships_one_owner_per_team_key ON memberships (team_id) WHERE role = 'owner';
```

If memberships can end and restart, store a validity range and forbid overlaps (5.5 or 8.7.4) instead of deleting rows.

### 8.3 Polymorphic associations and better alternatives

**Problem.** Comments can belong to a post *or* a photo. The ORM-style solution stores `commentable_type text` and `commentable_id bigint` in `comments`. No foreign key can protect `commentable_id`, so orphans and typos (`'Post'` vs `'post'`) creep in, and every query filters on two columns. Karwin lists it as an anti-pattern [46]; GitLab's rule is "Always use separate tables instead of polymorphic associations" [47].

**Alternative 1: exclusive arc.** One nullable foreign key per parent type, and a `CHECK` that exactly one is set [48].

```sql
CREATE TABLE comments (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    post_id     bigint REFERENCES posts (id)  ON DELETE CASCADE,
    photo_id    bigint REFERENCES photos (id) ON DELETE CASCADE,
    body        text        NOT NULL,
    created_at  timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT comments_one_parent_check CHECK (num_nonnulls(post_id, photo_id) = 1)
);
CREATE INDEX comments_post_id_idx  ON comments (post_id)  WHERE post_id IS NOT NULL;
CREATE INDEX comments_photo_id_idx ON comments (photo_id) WHERE photo_id IS NOT NULL;
```

**Alternative 2: one table per parent type** (`post_comments`, `photo_comments`), the GitLab approach [47].

**Alternative 3: a supertype table.** Every commentable thing owns a row in `commentables`; comments reference that one table.

```sql
CREATE TABLE commentables (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    kind  text NOT NULL CHECK (kind IN ('post', 'photo'))
);
CREATE TABLE posts (
    id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    commentable_id  bigint NOT NULL UNIQUE REFERENCES commentables (id),
    title           text   NOT NULL
);
CREATE TABLE comments (
    id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    commentable_id  bigint NOT NULL REFERENCES commentables (id) ON DELETE CASCADE,
    body            text   NOT NULL
);
```

| Approach | Foreign key integrity | Adding a parent type | Use when |
|---|---|---|---|
| `(type, id)` columns | none | free | avoid; acceptable only for logs where integrity does not matter |
| Exclusive arc | full | add a column, change the `CHECK` | 2–5 parent types |
| Table per parent type | full | add a table | types behave differently |
| Supertype table | full | new type references the supertype | many types share a feature (comments, likes, attachments) |

### 8.4 Subtypes and inheritance

**Problem.** A payment is either a card payment or a bank transfer. All payments share columns (amount, currency); each kind has its own columns. Martin Fowler names three mappings: single table, class table, and concrete table [49][50][51].

**Single-table inheritance:** one table, nullable kind-specific columns, guarded by `CHECK`.

```sql
CREATE TABLE payments (
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    kind          text   NOT NULL CHECK (kind IN ('card', 'bank_transfer')),
    amount_minor  bigint NOT NULL CHECK (amount_minor > 0),
    currency      text   NOT NULL REFERENCES currencies (code),
    card_last4    text,
    iban          text,
    CONSTRAINT payments_kind_fields_check CHECK (
        (kind = 'card'          AND card_last4 IS NOT NULL AND iban IS NULL) OR
        (kind = 'bank_transfer' AND iban IS NOT NULL       AND card_last4 IS NULL))
);
```

**Class-table inheritance:** a parent table plus one table per subtype. The kind is copied into the subtype and tied with a composite foreign key, so a card row can only attach to a `'card'` payment.

```sql
CREATE TABLE payments (
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    kind          text   NOT NULL CHECK (kind IN ('card', 'bank_transfer')),
    amount_minor  bigint NOT NULL CHECK (amount_minor > 0),
    currency      text   NOT NULL REFERENCES currencies (code),
    CONSTRAINT payments_id_kind_key UNIQUE (id, kind)
);
CREATE TABLE card_payments (
    payment_id  bigint PRIMARY KEY,
    kind        text   NOT NULL DEFAULT 'card' CHECK (kind = 'card'),
    card_last4  text   NOT NULL CHECK (card_last4 ~ '^[0-9]{4}$'),
    FOREIGN KEY (payment_id, kind) REFERENCES payments (id, kind) ON DELETE CASCADE
);
-- bank_transfer_payments: same shape, with kind = 'bank_transfer' and iban text NOT NULL
```

This design does not force every payment to have its subtype row; insert both rows in one transaction (or one function).

**Concrete-table inheritance:** one complete table per kind, no shared table. Listing all payments needs `UNION ALL`, and nothing can reference "any payment".

| Pattern | Pros | Cons | Use when |
|---|---|---|---|
| Single table | simple queries, one FK target | many NULLs, long `CHECK`s | few kinds, few specific columns |
| Class table | real `NOT NULL`s per kind, one FK target | joins, two inserts per row | kinds with many specific columns |
| Concrete table | no joins | no common FK target, `UNION ALL` for lists | kinds rarely used together |

Do **not** use PostgreSQL table inheritance (`INHERITS`) for this. Indexes, unique constraints, and foreign keys "only apply to single tables, not to their inheritance children" [52], and the wiki lists it under "Don't Do This" [4].

### 8.5 EAV and why to avoid it; `jsonb` as the modern alternative

**Problem.** Products have attributes that vary by category (shoe size, screen resolution). The EAV design (entity-attribute-value: one row per attribute) looks flexible but is "the worst possible design when it comes to performance" [26]: no types, no constraints, no foreign keys, and every read joins once per attribute [46].

```sql
-- Bad: EAV
CREATE TABLE product_attributes (
    product_id  bigint NOT NULL,
    attribute   text   NOT NULL,
    value       text,
    PRIMARY KEY (product_id, attribute)
);

-- Good: hybrid core columns + jsonb for the long tail
CREATE TABLE products (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku          text          NOT NULL UNIQUE,
    name         text          NOT NULL,
    price        numeric(12,2) NOT NULL CHECK (price >= 0),
    category_id  bigint        NOT NULL REFERENCES categories (id),
    attributes   jsonb         NOT NULL DEFAULT '{}'
                 CHECK (jsonb_typeof(attributes) = 'object')
);
CREATE INDEX products_attributes_gin_idx ON products USING gin (attributes jsonb_path_ops);

SELECT id, name FROM products WHERE attributes @> '{"color": "red"}';

-- A key that is filtered or sorted often: give it an index (and statistics), or promote it to a column
CREATE INDEX products_attr_size_idx ON products ((attributes ->> 'size'));
```

Rule: real columns for the known core; `jsonb` for the long tail [26]; promote a key to a column when you start filtering, sorting, or constraining on it often (4.4).

### 8.6 Soft delete

**Problem.** Users want "undo", auditors want history, and the law wants erasure. A `deleted_at` column looks like an easy answer but leaks into every query.

| Approach | How | Pros | Cons |
|---|---|---|---|
| Hard delete | `DELETE` | simple; foreign keys and cascades work; erasure is real | no undo; history lost unless audited (8.7) |
| Hard delete + archive table | trigger copies the old row as `jsonb` [54] | live tables stay clean; deleted data kept for rare needs | restore is manual; the archive needs its own retention |
| Soft delete column | `deleted_at timestamptz` | easy undo; references stay valid | every query must filter; uniqueness needs partial indexes; no cascades; dead data grows; personal data still stored [53] |

Brandur Leach reports that in over ten years (Heroku, Stripe, and later) he never saw anyone use soft deletion to actually undelete something, while the `deleted_at IS NULL` filter leaks into every query and foreign keys stop protecting you [53]. Prefer the archive table.

```sql
-- Hard delete + archive (generic trigger for any table with an id column)
CREATE TABLE deleted_records (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    table_name  text        NOT NULL,
    record_id   text        NOT NULL,
    data        jsonb       NOT NULL,
    deleted_at  timestamptz NOT NULL DEFAULT now()
);

CREATE FUNCTION archive_deleted_row() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO deleted_records (table_name, record_id, data)
  VALUES (TG_TABLE_NAME, OLD.id::text, to_jsonb(OLD));
  RETURN NULL;
END $$;

CREATE TRIGGER users_archive_on_delete
AFTER DELETE ON users
FOR EACH ROW EXECUTE FUNCTION archive_deleted_row();
```

If you soft delete anyway, do it fully:

```sql
ALTER TABLE users ADD COLUMN deleted_at timestamptz;

-- Uniqueness among live rows only: a deleted user's email can be reused
CREATE UNIQUE INDEX users_email_live_key ON users (lower(email)) WHERE deleted_at IS NULL;

-- Index what live queries need
CREATE INDEX users_live_created_at_idx ON users (created_at) WHERE deleted_at IS NULL;

-- A view so that code cannot forget the filter (recreate it when you add columns)
CREATE VIEW live_users AS
SELECT * FROM users WHERE deleted_at IS NULL;
```

- An RLS policy can also hide deleted rows ([11](11-security.md)).
- Erasure: GDPR Article 17 requires erasure of personal data "without undue delay" on a valid request [56]. Soft-deleted rows and archive copies are still personal data: plan a purge job (hard delete or anonymize after a short grace period) and decide how backups age out. Check the details with your legal team.

### 8.7 Audit trail and history

#### 8.7.1 Trigger-based audit table with `jsonb` diffs

**Problem.** "Who changed this order, when, and what was the old value?" The answer must be written in the same transaction as the change, or it can go missing.

```sql
CREATE TABLE audit_log (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    table_name  text        NOT NULL,
    record_id   text        NOT NULL,
    operation   text        NOT NULL CHECK (operation IN ('INSERT', 'UPDATE', 'DELETE')),
    old_data    jsonb,                 -- full old row (UPDATE, DELETE)
    new_data    jsonb,                 -- full new row (INSERT) or changed keys only (UPDATE)
    actor_id    text,                  -- set by the app, see below
    changed_at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX audit_log_record_idx ON audit_log (table_name, record_id, changed_at);
CREATE INDEX audit_log_changed_at_brin ON audit_log USING brin (changed_at);

CREATE FUNCTION audit_row_change() RETURNS trigger
LANGUAGE plpgsql AS $$
DECLARE
  old_row jsonb;
  new_row jsonb;
BEGIN
  IF TG_OP IN ('UPDATE', 'DELETE') THEN old_row := to_jsonb(OLD); END IF;
  IF TG_OP IN ('INSERT', 'UPDATE') THEN new_row := to_jsonb(NEW); END IF;

  IF TG_OP = 'UPDATE' THEN
    -- keep only the keys whose value changed
    SELECT jsonb_object_agg(n.key, n.value) INTO new_row
    FROM jsonb_each(to_jsonb(NEW)) AS n
    WHERE n.value IS DISTINCT FROM old_row -> n.key;
    IF new_row IS NULL THEN
      RETURN NULL;  -- no-op update: nothing to log
    END IF;
  END IF;

  INSERT INTO audit_log (table_name, record_id, operation, old_data, new_data, actor_id)
  VALUES (TG_TABLE_NAME,
          coalesce(old_row ->> 'id', new_row ->> 'id'),
          TG_OP, old_row, new_row,
          nullif(current_setting('app.actor_id', true), ''));
  RETURN NULL;
END $$;

CREATE TRIGGER orders_audit
AFTER INSERT OR UPDATE OR DELETE ON orders
FOR EACH ROW EXECUTE FUNCTION audit_row_change();
```

```sql
-- In the application transaction: transaction-scoped setting, safe with connection poolers
BEGIN;
SELECT set_config('app.actor_id', '42', true);
UPDATE orders SET status = 'shipped' WHERE id = 1001;
COMMIT;
```

- `jsonb` snapshots survive schema changes: no audit migration when a column is added [57].
- Triggers slow writes; Supabase's version of this design suggests other tools for tables above roughly 1,000 writes per second [57].
- `TRUNCATE` does not fire row-level triggers.
- Large audit tables: partition by month and drop old partitions (8.13).
- For statement-level audit logging (who ran which SQL), see pgAudit in [11](11-security.md).

#### 8.7.2 History tables (system-versioning emulation)

**Problem.** "What was the price of product 42 on 1 March?" PostgreSQL "does not currently support system time" (automatic row versioning) [58]. Emulate it with the current table plus a history table filled by a trigger.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE product_prices (
    product_id  bigint        PRIMARY KEY REFERENCES products (id),
    amount      numeric(12,2) NOT NULL,
    valid_from  timestamptz   NOT NULL DEFAULT now()
);
CREATE TABLE product_prices_history (
    product_id  bigint        NOT NULL,
    amount      numeric(12,2) NOT NULL,
    valid       tstzrange     NOT NULL,
    CONSTRAINT product_prices_history_no_overlap_excl
        EXCLUDE USING gist (product_id WITH =, valid WITH &&)
);

CREATE FUNCTION product_prices_keep_history() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO product_prices_history (product_id, amount, valid)
  VALUES (OLD.product_id, OLD.amount, tstzrange(OLD.valid_from, now()));
  IF TG_OP = 'UPDATE' THEN
    NEW.valid_from := now();
    RETURN NEW;
  END IF;
  RETURN OLD;
END $$;

CREATE TRIGGER product_prices_history_trg
BEFORE UPDATE OR DELETE ON product_prices
FOR EACH ROW EXECUTE FUNCTION product_prices_keep_history();

-- Price at a point in time
SELECT amount FROM product_prices
WHERE product_id = 42 AND valid_from <= '2026-03-01 00:00+00'
UNION ALL
SELECT amount FROM product_prices_history
WHERE product_id = 42 AND valid @> '2026-03-01 00:00+00'::timestamptz;
```

Two updates in one transaction share the same `now()` and store an empty range (harmless, but visible). Ready-made versions exist: the `temporal_tables` C extension [60] and a PL/pgSQL port for managed databases [61].

#### 8.7.3 Event sourcing

**Problem.** The history of changes *is* the product (ledgers, workflows, collaborative editing). Event sourcing stores every change as an immutable event and derives the current state from the events [62].

```sql
CREATE TABLE events (
    id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    stream_id       uuid        NOT NULL,   -- one aggregate, e.g. one order
    stream_version  integer     NOT NULL,   -- 1, 2, 3... inside the stream
    event_type      text        NOT NULL,
    payload         jsonb       NOT NULL,
    occurred_at     timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT events_stream_version_key UNIQUE (stream_id, stream_version)
);

-- Optimistic concurrency: the writer read version 6. If another writer already
-- appended version 7, this insert fails with 23505 and the command is retried.
INSERT INTO events (stream_id, stream_version, event_type, payload)
VALUES ('01999d3a-7c2e-7b4a-9f10-2a3b4c5d6e7f', 7, 'OrderShipped', '{"carrier": "UPS"}');
```

- **Projections** are ordinary tables (`order_summaries`) built from events, in the same transaction or later; they can be rebuilt by replaying.
- Fowler's warnings: replays must not re-trigger external side effects, and event formats and business rules change over time [62].
- Readers that poll "events with `id` greater than the last one I saw" can miss rows: identity values are assigned at insert time, but transactions commit in a different order. Poll with a safety margin or use logical decoding (see [08](08-transactions-concurrency-locking.md)).
- Do not choose event sourcing by default; an audit table (8.7.1) answers most "who changed what" questions.

#### 8.7.4 Temporal keys (PG 18+)

PG 18 adds non-overlapping keys over ranges: `WITHOUT OVERLAPS` on the last column of a `PRIMARY KEY` or `UNIQUE` constraint, and `PERIOD` on the last column of a foreign key [1][2].

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;  -- needed for the plain bigint column in the key

CREATE TABLE room_rates (
    room_id   bigint        NOT NULL REFERENCES rooms (id),
    valid_at  daterange     NOT NULL,
    rate      numeric(10,2) NOT NULL,
    PRIMARY KEY (room_id, valid_at WITHOUT OVERLAPS)
);

CREATE TABLE room_rate_discounts (
    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room_id   bigint       NOT NULL,
    valid_at  daterange    NOT NULL,
    percent   numeric(5,2) NOT NULL CHECK (percent BETWEEN 0 AND 100),
    FOREIGN KEY (room_id, PERIOD valid_at) REFERENCES room_rates (room_id, PERIOD valid_at)
);
```

Verified scope [1][2][58][59]:

- The `WITHOUT OVERLAPS` column must be a range or multirange; empty ranges are rejected; the constraint uses a GiST index; other key columns need `btree_gist` unless they are ranges.
- A `PERIOD` foreign key is satisfied when the referenced rows *together cover* the whole period of the referencing row.
- Temporal foreign keys support only `NO ACTION`: no `CASCADE`, `SET NULL`, `SET DEFAULT`, or `RESTRICT`.
- There is no `UPDATE/DELETE ... FOR PORTION OF` in PG 18, and it is not in the PG 19 beta release notes either. There is no system time.

#### 8.7.5 Slowly changing dimensions (briefly)

From data warehousing: **type 1** overwrites the old value (no history); **type 2** adds a new row per change, with a validity start, a validity end, and a current-row flag [63]. In an OLTP schema, type 2 is the history table of 8.7.2, or a versions table with a partial unique index on the current row:

```sql
CREATE UNIQUE INDEX customer_versions_current_key
    ON customer_versions (customer_id) WHERE valid_to IS NULL;
```

### 8.8 Status columns and state machines

**Problem.** An order moves `pending → paid → shipped → delivered`, and some moves are forbidden (`shipped → pending`). A bare status column accepts any value change.

Three layers, use as many as you need:

1. **Valid values:** `CHECK` list, enum, or lookup table (4.2).
2. **Timestamps per state, tied to the status:** `paid_at`, `shipped_at`, plus checks such as `CHECK (status NOT IN ('shipped', 'delivered') OR shipped_at IS NOT NULL)`.
3. **Valid transitions:** a transition table and a trigger.

```sql
CREATE TABLE order_status_transitions (
    from_status  text NOT NULL,
    to_status    text NOT NULL,
    PRIMARY KEY (from_status, to_status)
);
INSERT INTO order_status_transitions (from_status, to_status) VALUES
    ('pending', 'paid'), ('pending', 'cancelled'),
    ('paid', 'shipped'), ('paid', 'refunded'),
    ('shipped', 'delivered');

CREATE FUNCTION orders_check_transition() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  IF NEW.status IS DISTINCT FROM OLD.status AND NOT EXISTS (
       SELECT 1 FROM order_status_transitions
       WHERE from_status = OLD.status AND to_status = NEW.status) THEN
    RAISE EXCEPTION 'invalid order status transition: % -> %', OLD.status, NEW.status
      USING ERRCODE = 'check_violation';
  END IF;
  RETURN NEW;
END $$;

CREATE TRIGGER orders_check_transition
BEFORE UPDATE OF status ON orders
FOR EACH ROW EXECUTE FUNCTION orders_check_transition();

-- Application side: a guarded update. 0 rows = wrong state or a concurrent change.
UPDATE orders
SET status = 'shipped', shipped_at = now()
WHERE id = 1001 AND status = 'paid'
RETURNING id;
```

If you need the full history of states, append rows to an `order_status_changes` table (who, when, from, to) in the same transaction, with a foreign key to the transition table. Another approach computes the state with a custom aggregate over an event table [64].

### 8.9 Job queue tables with `SKIP LOCKED`

**Problem.** Background work (emails, PDF generation, embeddings) must run outside the request, survive crashes, and be shared by several workers without two workers taking the same job.

**Why `SKIP LOCKED`.** `SELECT ... FOR UPDATE SKIP LOCKED` locks the selected rows and *skips* rows already locked by others instead of waiting. The docs say this gives "an inconsistent view of the data", so it is not for general queries, but it is designed for "multiple consumers accessing a queue-like table" [65].

```sql
CREATE TABLE jobs (
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    queue         text        NOT NULL DEFAULT 'default',
    kind          text        NOT NULL,
    payload       jsonb       NOT NULL DEFAULT '{}',
    status        text        NOT NULL DEFAULT 'pending'
                  CHECK (status IN ('pending', 'running', 'succeeded', 'failed')),
    priority      smallint    NOT NULL DEFAULT 0,
    run_at        timestamptz NOT NULL DEFAULT now(),
    attempts      integer     NOT NULL DEFAULT 0,
    max_attempts  integer     NOT NULL DEFAULT 5,
    locked_until  timestamptz,
    locked_by     text,
    last_error    text,
    created_at    timestamptz NOT NULL DEFAULT now(),
    finished_at   timestamptz
);

-- Only runnable jobs are indexed: the index stays small even if the table is big
CREATE INDEX jobs_runnable_idx ON jobs (queue, priority DESC, run_at) WHERE status = 'pending';
CREATE INDEX jobs_lease_idx ON jobs (locked_until) WHERE status = 'running';
```

Claim a batch with a **lease** (a lock with an expiry time), then commit at once and do the work outside the transaction:

```sql
WITH next_jobs AS (
    SELECT id
    FROM jobs
    WHERE status = 'pending' AND queue = 'emails' AND run_at <= now()
    ORDER BY priority DESC, run_at
    LIMIT 10
    FOR UPDATE SKIP LOCKED
)
UPDATE jobs AS j
SET status = 'running',
    attempts = j.attempts + 1,
    locked_until = now() + interval '5 minutes',
    locked_by = 'worker-7'
FROM next_jobs
WHERE j.id = next_jobs.id
RETURNING j.id, j.kind, j.payload, j.attempts;
```

```sql
-- Success: delete (keeps the table small) or mark as done
UPDATE jobs SET status = 'succeeded', finished_at = now(), locked_until = NULL
WHERE id = 1001 AND locked_by = 'worker-7';

-- Failure: retry with exponential backoff, or give up
UPDATE jobs
SET status       = CASE WHEN attempts >= max_attempts THEN 'failed' ELSE 'pending' END,
    run_at       = now() + least(interval '1 hour', interval '10 seconds' * power(2, attempts)),
    last_error   = 'SMTP timeout',
    locked_until = NULL,
    locked_by    = NULL
WHERE id = 1001;

-- Reaper, every minute: leases of crashed workers expire (the "visibility timeout")
UPDATE jobs
SET status       = CASE WHEN attempts >= max_attempts THEN 'failed' ELSE 'pending' END,
    last_error   = coalesce(last_error, 'lease expired'),
    locked_until = NULL,
    locked_by    = NULL
WHERE status = 'running' AND locked_until < now();
```

| Claim style | How | Pros | Cons |
|---|---|---|---|
| Lock for the whole job | `BEGIN`; claim with `SKIP LOCKED`; work; finish; `COMMIT` | a crash releases the job automatically; no reaper | one open transaction and one connection per running job; long transactions block vacuum |
| Lease (shown above) | claim + commit; finish later | short transactions; long jobs are fine | needs a reaper; a job can run twice |

Design rules:

- **Jobs must be idempotent** (safe to run twice): with leases, at-least-once execution is the normal case.
- **Enqueue in the same transaction as the business change.** The job exists if and only if the change committed. This "transactional enqueueing" is the main advantage over an external broker [67][70].
- **Fight bloat.** Every claim and every finish writes a new row version. Dead rows pile up, and long-running transactions anywhere in the database stop vacuum from removing them. In a 2015 test (before `SKIP LOCKED` existed, but the dead-row effect is the same), Brandur Leach saw job lock time grow from under 0.01 s to over 0.1 s and a backlog of 60,000 jobs within an hour, with a long-running transaction open [66]. Keep the hot table small (delete finished jobs or move them to a history table), give it aggressive per-table autovacuum settings, and limit long transactions ([08](08-transactions-concurrency-locking.md), [09](09-operations-and-server-tuning.md)).
- **Wake workers with `LISTEN/NOTIFY`** instead of tight polling (Graphile Worker reports under 3 ms from enqueue to execution [68]). Recall.ai reported in 2025 that, at very high write rates, commits that send `NOTIFY` were serialized by a global lock [71]: use it as a wake-up hint and keep a polling fallback.

Libraries (status checked October 2026):

| Library | Stack | Notes |
|---|---|---|
| pg-boss | Node.js 22.12+, PostgreSQL 13+ | `SKIP LOCKED`; create jobs inside your transaction; retries with backoff, cron, dead-letter queues; adapters for Prisma, Drizzle, Knex, Kysely [67] |
| Graphile Worker | Node.js | `SKIP LOCKED` + `LISTEN/NOTIFY`, low latency [68] |
| PGMQ | PostgreSQL extension, PG 14–18; any language | SQS-like API: visibility timeout, archive instead of delete; repository now under the `pgmq` organization [69] |
| River | Go | transactional enqueueing [70] |

Stay in PostgreSQL while jobs are tied to database changes and the volume is moderate. Move to a broker (Kafka, RabbitMQ, SQS) when you need very high throughput, fan-out to many independent consumers, long replayable streams, or when queue churn causes vacuum problems you cannot tune away.

### 8.10 Transactional outbox, idempotency keys, inbox

**Problem.** "Save the order, then publish `OrderPaid` to the broker" is a *dual write*: if the process crashes between the two, the event is lost (or sent for an order that rolled back). A distributed transaction across the database and the broker is not viable [72].

**Transactional outbox.** Write the event into an outbox table in the same transaction as the change; a separate relay publishes it [72].

```sql
CREATE TABLE outbox_events (
    id              uuid        PRIMARY KEY DEFAULT gen_random_uuid(),  -- uuidv7() on PG 18
    aggregate_type  text        NOT NULL,       -- 'order'
    aggregate_id    text        NOT NULL,       -- '1001'
    event_type      text        NOT NULL,       -- 'OrderPaid'
    payload         jsonb       NOT NULL,
    created_at      timestamptz NOT NULL DEFAULT now(),
    published_at    timestamptz
);
CREATE INDEX outbox_events_unpublished_idx ON outbox_events (created_at) WHERE published_at IS NULL;

BEGIN;
UPDATE orders SET status = 'paid', paid_at = now() WHERE id = 1001;
INSERT INTO outbox_events (aggregate_type, aggregate_id, event_type, payload)
VALUES ('order', '1001', 'OrderPaid', '{"order_id": 1001, "amount_minor": 1999}');
COMMIT;
```

- **Relay:** either a poller (claim unpublished rows with `FOR UPDATE SKIP LOCKED`, publish, set `published_at` or delete) or log tailing with change data capture; Debezium's outbox router expects columns like `id`, `aggregatetype`, `aggregateid`, `type`, `payload` [74].
- **At-least-once:** the relay can publish a message twice after a crash, so consumers must be idempotent [72].
- **Cleanup:** delete or partition published rows; the outbox is a queue table (8.9).

**Inbox (idempotent consumer).** The consumer records each message id in the same transaction as its side effects; the primary key rejects duplicates [73].

```sql
CREATE TABLE processed_messages (
    consumer      text        NOT NULL,
    message_id    uuid        NOT NULL,
    processed_at  timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (consumer, message_id)
);

BEGIN;
INSERT INTO processed_messages (consumer, message_id)
VALUES ('billing', '01999d3a-7c2e-7b4a-9f10-2a3b4c5d6e7f')
ON CONFLICT DO NOTHING
RETURNING message_id;   -- no row returned = duplicate: skip the work and COMMIT
-- ... side effects of the message, in the same transaction ...
COMMIT;
```

**Idempotency keys for APIs** (Stripe style). The client sends a unique key with each mutating request; the server stores the key, the request, and the final response, so a retry returns the stored response instead of charging twice [75].

```sql
CREATE TABLE idempotency_keys (
    id               bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id          bigint      NOT NULL REFERENCES users (id),
    idempotency_key  text        NOT NULL CHECK (char_length(idempotency_key) <= 100),
    request_method   text        NOT NULL,
    request_path     text        NOT NULL,
    request_params   jsonb       NOT NULL,
    recovery_point   text        NOT NULL DEFAULT 'started',  -- progress through the request
    locked_at        timestamptz DEFAULT now(),               -- a request is working on it
    response_code    integer,
    response_body    jsonb,
    created_at       timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT idempotency_keys_user_key_key UNIQUE (user_id, idempotency_key)
);
```

Flow: insert the key (`ON CONFLICT` → load the existing row: finished → return the stored response; locked → answer 409; different parameters → reject); run the work in "atomic phases" that advance `recovery_point`; store the response. Brandur's reference design wraps each phase in a `SERIALIZABLE` transaction and deletes keys with a reaper after about 72 hours [75].

### 8.11 Counters and hot rows

**Problem.** `UPDATE post_stats SET views = views + 1 WHERE post_id = 42` from many sessions at once: each writer waits for the row lock until the previous transaction commits, and each update leaves a dead row version. A single popular row becomes a *hot row* that serializes your traffic (see [08](08-transactions-concurrency-locking.md)).

| Option | Exact? | Contention | Use when |
|---|---|---|---|
| Count on demand with an index | yes | none | small counts, rare reads |
| Slotted (sharded) counter | yes | divided by the number of slots | frequent increments on few rows [78] |
| Append events, roll up later | yes, after the roll-up | none | analytics, views, likes |
| Batch in the app, flush periodically | almost (a crash loses the buffer) | very low | very high rates |
| Estimate from statistics | no | none | "about 1.2 M rows" displays [76][77] |

```sql
-- Slotted counter: 16 rows per post, pick one at random, sum on read
CREATE TABLE post_view_counters (
    post_id  bigint   NOT NULL REFERENCES posts (id) ON DELETE CASCADE,
    slot     smallint NOT NULL CHECK (slot BETWEEN 0 AND 15),
    views    bigint   NOT NULL DEFAULT 0,
    PRIMARY KEY (post_id, slot)
);

INSERT INTO post_view_counters (post_id, slot, views)
VALUES (42, floor(random() * 16)::smallint, 1)
ON CONFLICT (post_id, slot) DO UPDATE SET views = post_view_counters.views + 1;

SELECT sum(views) AS views FROM post_view_counters WHERE post_id = 42;

-- Whole-table estimate (planner statistics; -1 means never vacuumed or analyzed)
SELECT reltuples::bigint AS estimated_rows FROM pg_class WHERE oid = 'public.orders'::regclass;
```

`reltuples` is "only an estimate used by the planner" [77]; Laurenz Albe notes it is updated by autovacuum and autoanalyze and "should never be much more than 10% off" [76].

### 8.12 Multi-tenancy

**Problem.** A SaaS application serves many customer organizations (tenants). Each tenant must see only its own data.

| Model | Isolation | Scale (Crunchy Data guidance [79]) | Operations | Use when |
|---|---|---|---|---|
| Shared tables + `tenant_id` | logical; RLS as a safety net | up to millions of tenants | lowest: one schema, one migration | default for SaaS |
| Schema per tenant | namespace | hundreds of tenants | every migration runs once per schema; `search_path` per connection | a few large tenants needing custom tables |
| Database per tenant | strongest; per-tenant backup and restore | tens of tenants ("if you anticipate 50 customers or more steer clear") | highest: N databases, N pools, N migrations | strict isolation, data residency, per-tenant restore |

Shared-table rules:

- `tenant_id NOT NULL` on **every** tenant-owned table, even when it could be derived through a join; Crunchy calls this a good step to denormalize [79].
- Put `tenant_id` **first** in primary keys, unique constraints, and indexes, so each tenant's rows cluster in the index and every lookup starts with the tenant.
- Use **composite foreign keys** that include `tenant_id`; a row can then never point at another tenant's row.
- Add row-level security policies as defense in depth ([11](11-security.md)).

```sql
CREATE TABLE tenants (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name  text NOT NULL
);

CREATE TABLE users (
    tenant_id  bigint NOT NULL REFERENCES tenants (id) ON DELETE CASCADE,
    id         bigint GENERATED ALWAYS AS IDENTITY,
    email      text   NOT NULL,
    PRIMARY KEY (tenant_id, id),
    CONSTRAINT users_tenant_email_key UNIQUE (tenant_id, email)
);

CREATE TABLE projects (
    tenant_id   bigint      NOT NULL REFERENCES tenants (id) ON DELETE CASCADE,
    id          bigint GENERATED ALWAYS AS IDENTITY,
    owner_id    bigint,
    name        text        NOT NULL,
    created_at  timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (tenant_id, id),
    FOREIGN KEY (tenant_id, owner_id) REFERENCES users (tenant_id, id)
        ON DELETE SET NULL (owner_id)   -- PG 15+: keep tenant_id, clear only owner_id
);
CREATE INDEX projects_tenant_owner_idx ON projects (tenant_id, owner_id);
CREATE INDEX projects_tenant_created_at_idx ON projects (tenant_id, created_at DESC);
```

On PG 14, `ON DELETE SET NULL` cannot take a column list; use `NO ACTION` and clear `owner_id` in the application, or a trigger. If you prefer a single-column primary key, keep `id` as the key and add `UNIQUE (tenant_id, id)` as the target of the composite foreign keys.

**Scaling out.** Citus distributes tables by a distribution column (the tenant id) across nodes and "requires that primary and foreign key constraints include the distribution column" [80], which is exactly the layout above. Citus 14.x supports PG 16–18 [81].

### 8.13 Partitioning design

**What it is.** One logical table split into child tables (partitions) by a partition key. Queries go to the parent; the planner skips partitions that cannot match (*partition pruning*).

**When it helps** [82]:

- The table is very large: "a rule of thumb is that the size of the table should exceed the physical memory of the database server".
- Retention: dropping or detaching a partition "is far faster than a bulk operation" and avoids the `VACUUM` cost of a mass `DELETE`.
- Most queries touch one or a few partitions (recent data).

**When it hurts:**

- Queries that do not filter on the partition key visit every partition.
- More partitions mean more planning time and more memory per session; the planner handles "up to a few thousand partitions fairly well" only when pruning leaves few of them [82].
- Primary keys and unique constraints must include the partition key, so a column like `email` cannot be globally unique [82].
- It is not a replacement for indexes. "Never just assume that more partitions are better than fewer partitions, nor vice-versa" [82].

| Method | Example key | Good for |
|---|---|---|
| `RANGE` | `created_at` by month | time series, logs, events, audit; retention |
| `LIST` | `region`, plan tier | a few discrete values handled differently |
| `HASH` | `tenant_id`, modulus 16 | spreading data and vacuum work evenly; no retention benefit |

Choose the key that appears in most `WHERE` clauses and that your retention deletes by [82].

```sql
CREATE TABLE events (
    id          bigint GENERATED ALWAYS AS IDENTITY,  -- PG 17+; on PG 14–16 use a uuid or a sequence default
    tenant_id   bigint      NOT NULL,
    created_at  timestamptz NOT NULL,
    kind        text        NOT NULL,
    payload     jsonb       NOT NULL DEFAULT '{}',
    PRIMARY KEY (id, created_at)          -- must include the partition key
) PARTITION BY RANGE (created_at);

-- Explicit UTC offsets: a bare '2026-10-01' would use the session time zone
CREATE TABLE events_2026_10 PARTITION OF events
    FOR VALUES FROM ('2026-10-01 00:00+00') TO ('2026-11-01 00:00+00');
CREATE TABLE events_2026_11 PARTITION OF events
    FOR VALUES FROM ('2026-11-01 00:00+00') TO ('2026-12-01 00:00+00');

-- An index on the parent is created on every partition
CREATE INDEX events_tenant_created_at_idx ON events (tenant_id, created_at);

-- Retention: remove a whole month without DELETE and without VACUUM
ALTER TABLE events DETACH PARTITION events_2025_10 CONCURRENTLY;
DROP TABLE events_2025_10;
```

- `DETACH ... CONCURRENTLY` cannot run inside a transaction block and is refused when the table has a default partition [83].
- A `DEFAULT` partition catches rows that match no partition. Keep it empty: creating a new partition scans the default partition for rows that would belong to it [83].
- Identity columns on partitioned tables need PG 17+ [13]; exclusion constraints on partitioned tables need PG 17+ and must compare the partition key with equality [13][1].
- Foreign keys *to* a partitioned table must reference its primary key, which includes the partition key; referencing tables then need that column too.
- Automate partition creation and retention with **pg_partman** (PG 14+; version 5.x supports only declarative partitioning; optional background worker) [84]. Index creation and partition changes on live systems: [10](10-safe-schema-migrations.md).

### 8.14 Smaller patterns

**Tags: array or join table?**

| | `text[]` column + GIN | Join table (`post_tags`) |
|---|---|---|
| Read with the row | one row, no join | join or aggregate |
| Search "has tag X" | `tags @> ARRAY['x']` with GIN | index on `(tag_id, post_id)` |
| Rename or merge a tag | update every row | update one row |
| Tag metadata, counts, FKs | no | yes |
| Use when | free-form labels, small lists | managed tag vocabulary |

```sql
ALTER TABLE documents ADD COLUMN tags text[] NOT NULL DEFAULT '{}';
CREATE INDEX documents_tags_gin_idx ON documents USING gin (tags);
SELECT id, title FROM documents WHERE tags @> ARRAY['invoice'];
```

**User settings: `jsonb` with defaults.** Defaults live in code or in one SQL literal; rows store only overrides.

```sql
CREATE TABLE user_settings (
    user_id     bigint      PRIMARY KEY REFERENCES users (id) ON DELETE CASCADE,
    settings    jsonb       NOT NULL DEFAULT '{}' CHECK (jsonb_typeof(settings) = 'object'),
    updated_at  timestamptz NOT NULL DEFAULT now()
);
-- Effective settings: the right side wins
SELECT '{"theme": "light", "digest": "weekly"}'::jsonb || settings AS effective
FROM user_settings WHERE user_id = 42;
-- Change one key
UPDATE user_settings SET settings = jsonb_set(settings, '{theme}', '"dark"') WHERE user_id = 42;
```

**Files and blobs: store the bytes outside, the metadata inside.** Files in the database make backups slower and grow memory needs; files outside can drift out of sync with their rows [88]. Use object storage for bytes, and a table for metadata and integrity:

```sql
CREATE TABLE files (
    id            uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
    owner_id      bigint      NOT NULL REFERENCES users (id),
    storage_key   text        NOT NULL UNIQUE,   -- object key in the bucket
    content_type  text        NOT NULL,
    size_bytes    bigint      NOT NULL CHECK (size_bytes >= 0),
    sha256        bytea       NOT NULL CHECK (octet_length(sha256) = 32),
    status        text        NOT NULL DEFAULT 'uploading'
                  CHECK (status IN ('uploading', 'ready', 'deleting')),
    created_at    timestamptz NOT NULL DEFAULT now()
);
```

Run a reconciliation job that removes objects without a row and rows stuck in `uploading`.

**Document versioning: immutable versions plus a pointer.** The circular foreign key is deferred so that a document and its first version can be inserted in one transaction.

```sql
CREATE TABLE documents (
    id                  uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
    owner_id            bigint      NOT NULL REFERENCES users (id),
    current_version_no  integer,
    created_at          timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE document_versions (
    document_id  uuid        NOT NULL REFERENCES documents (id) ON DELETE CASCADE,
    version_no   integer     NOT NULL CHECK (version_no > 0),
    title        text        NOT NULL,
    body         text        NOT NULL,
    created_by   bigint      NOT NULL REFERENCES users (id),
    created_at   timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (document_id, version_no)
);
ALTER TABLE documents
    ADD CONSTRAINT documents_current_version_fkey
    FOREIGN KEY (id, current_version_no) REFERENCES document_versions (document_id, version_no)
    DEFERRABLE INITIALLY DEFERRED;
```

To add a version, lock the document row (`SELECT ... FOR UPDATE`), insert `max(version_no) + 1`, and move the pointer, all in one transaction.

**Translations (i18n).** A translation table per translatable entity, with a fallback locale:

```sql
CREATE TABLE product_translations (
    product_id   bigint NOT NULL REFERENCES products (id) ON DELETE CASCADE,
    locale       text   NOT NULL CHECK (locale ~ '^[a-z]{2}(-[A-Z]{2})?$'),
    name         text   NOT NULL,
    description  text,
    PRIMARY KEY (product_id, locale)
);

-- French if present, else English
SELECT DISTINCT ON (t.product_id) t.product_id, t.name
FROM product_translations AS t
WHERE t.locale IN ('fr-FR', 'en')
ORDER BY t.product_id, (t.locale = 'fr-FR') DESC;
```

For a few fields and a few locales, a `jsonb` column (`{"en": "...", "fr": "..."}`) is simpler but cannot require a locale or index each one easily.

**Money and currency.** Store the amount and its currency in the same row; never sum across currencies.

- Integer minor units (`amount_minor bigint`: 1999 = 19.99 EUR, 500 = 500 JPY) match payment APIs: Stripe expects amounts in the currency's smallest unit (1099 for 10.99 USD, 10 for 10 JPY, a zero-decimal currency) [89]. Keep `minor_unit` per currency (3.1).
- `numeric(19,4)` suits prices with sub-cent precision, tax calculations, and exchange rates.
- Never `money` (one currency per database setting, no fractions of a cent) [4], never floats [46].
- Exchange rates are their own table with a validity time; store the rate used on each converted row.

```sql
SELECT currency, sum(amount_minor) AS total_minor
FROM payments
GROUP BY currency;
```

**Time series.** Append-only rows ordered by time:

- A BRIN index (block range index) on the time column is tiny and works because rows arrive in time order: BRIN is "designed for handling very large tables in which certain columns have some natural correlation with their physical location" [86]. Details in [05](05-indexing.md).
- Range partitioning by time plus retention by `DROP` (8.13).
- TimescaleDB (by Tiger Data, formerly Timescale) adds hypertables (automatic time partitions), columnstore compression, and continuous aggregates; part of it is under the Timescale License rather than Apache 2.0 [87].

```sql
CREATE INDEX metrics_recorded_at_brin ON metrics USING brin (recorded_at);
```

**Documents and chunks for search and RAG.** Keep the source document, its versions, and its chunks as separate tables: `chunks (document_id, version_no, chunk_no, content, embedding)` with `ON DELETE CASCADE` from the document, `tenant_id` copied onto chunks for filtering, and a content hash to skip re-embedding unchanged text. Index types, hybrid search, and pgvector schemas are in [12](12-full-text-and-vector-search.md).

## 9. Schema anti-patterns

Most names come from Bill Karwin's *SQL Antipatterns, Volume 1* (2022) [46].

| Anti-pattern | Symptom | Why it hurts | Fix |
|---|---|---|---|
| Comma-separated list ("Jaywalking") | `tag_ids text` = `'1,5,9'` | no foreign keys, no index, `LIKE '%,5,%'` scans, no check on the elements | join table or array (8.14) |
| Repeated columns ("Multicolumn Attributes") | `tag1`, `tag2`, `tag3` | fixed maximum, `OR` across columns, many NULLs | child table (2.1) |
| Table per year or per customer ("Metadata Tribbles") | `orders_2025`, `orders_2026` created by the app | every query needs `UNION`; every change runs N times | one table; native partitioning if huge (8.13) |
| Missing foreign keys ("Keyless Entry") | orphan rows | integrity depends on every code path being perfect | foreign keys + indexes (5.4) |
| `id` on every table ("ID Required") | join table with its own `id`, duplicate pairs | duplicates allowed, extra index | composite primary key (3.6) |
| Floats for money ("Rounding Errors") | `0.1::float8 + 0.2::float8 = 0.3` is false | rounding drift in totals | `numeric` or integer minor units (8.14) |
| Enum for a changing list ("31 Flavors") | frequent `ALTER TYPE`, values that cannot be removed | migrations, no metadata | lookup table or `CHECK` (4.2) |
| File paths without integrity ("Phantom Files") | path column, file missing on disk | the database cannot check files or back them up | metadata table + reconciliation job (8.14) |
| Polymorphic `(type, id)` ("Polymorphic Associations") | no foreign key possible | orphans, typos | exclusive arc, per-type tables, supertype (8.3) |
| EAV ("Entity-Attribute-Value") | `attribute`, `value text` rows | no types, no constraints, slow pivots | columns + `jsonb` (8.5) |
| One true lookup table | `codes(type, code, label)` for every code list | foreign keys cannot target one list; mixed types; shared locking [90] | one table per list, or `CHECK` |
| God table | 80 columns, many nullable, several concerns | wide rows, lock contention, unclear ownership | split by concern; 1:1 tables for optional groups (7.1) |
| Quoted mixed-case names | `"User"."createdAt"` | quotes forever, easy mistakes [4] | lowercase `snake_case` (6.1) |
| Legacy types | `serial`, `timestamp`, `char(n)`, `money`, `varchar(n)` by reflex | see [4] | identity, `timestamptz`, `text` + `CHECK`, `numeric` |
| Table inheritance for subtypes | `INHERITS` | indexes and foreign keys do not span children [52] | patterns of 8.4 |

## 10. Documenting and reviewing a schema

### 10.1 `COMMENT ON`

Comments live in the database, next to the objects, and are shown by `\d+` in psql and by most GUI tools [91].

```sql
COMMENT ON TABLE orders IS
    'One customer order. Created at checkout. Never deleted: legal retention is 10 years.';
COMMENT ON COLUMN orders.total_minor IS
    'Order total in minor units of orders.currency, taxes included.';
COMMENT ON CONSTRAINT orders_total_check ON orders IS
    'Totals are never negative; refunds are separate rows in refunds.';

-- Read them back
SELECT col_description('orders'::regclass, attnum) AS comment, attname
FROM pg_attribute
WHERE attrelid = 'orders'::regclass AND attnum > 0 AND NOT attisdropped;
```

- Explain *why* and *meaning* (units, NULL meaning, who writes the column), not what the name already says.
- Comments are visible to every user of the database: no secrets [91].

### 10.2 ER diagrams

Generate diagrams from the live schema (or from migrations) instead of drawing them by hand, so they cannot drift. Tools are listed in [13](13-tools-by-use-case.md). Keep one diagram per bounded area (billing, content, identity) rather than one giant picture.

### 10.3 Schema review checklist

Use this list for every new table or migration (AI agents: check each item before proposing DDL).

**Modeling**

- [ ] The table represents one entity or one relationship, named after it (plural `snake_case`).
- [ ] Every non-key column depends on the key, the whole key, and nothing but the key; any copy is a deliberate snapshot or a documented denormalization.
- [ ] No lists in strings, no repeated columns, no EAV, no `(type, id)` pairs without foreign keys.

**Keys**

- [ ] Primary key: `bigint GENERATED ALWAYS AS IDENTITY` or UUIDv7 (not `serial`, not `integer` for growing tables, not random UUIDv4 for big write-heavy tables).
- [ ] Natural keys have a `UNIQUE` constraint (case-insensitive where needed).
- [ ] Ids exposed publicly do not reveal what they should not (volume, creation time); access is still checked.

**Columns and types**

- [ ] Every column is `NOT NULL` unless NULL has a documented meaning.
- [ ] `timestamptz` for instants, `date` for dates, `numeric` or minor units for money, `text` + `CHECK` for bounded strings.
- [ ] Booleans are not hiding a multi-state status; units appear in names (`_ms`, `_bytes`, `_minor`).
- [ ] `jsonb` columns have a shape `CHECK`, and hot keys have an index or a real column.

**Constraints**

- [ ] Every invariant from section 1 is a constraint, or its enforcement point is documented.
- [ ] Every foreign key has a deliberate `ON DELETE` action and an index on the referencing columns.
- [ ] Constraints have explicit names; the app maps their errors to messages.
- [ ] Multi-tenant tables: `tenant_id NOT NULL`, first in keys and indexes, inside composite foreign keys.

**Lifecycle and growth**

- [ ] Deletion strategy chosen (hard delete, archive, or soft delete with partial unique indexes) and personal data can be erased.
- [ ] History needs covered (audit trigger, history table, or events), written in the same transaction.
- [ ] Expected size and growth known; partitioning considered only for very large or retention-driven tables.
- [ ] Hot rows avoided (counters, status rows updated by many sessions).
- [ ] Queue-like tables have a partial index, a cleanup path, and autovacuum settings.

**Documentation and rollout**

- [ ] `COMMENT ON` for the table and for every non-obvious column.
- [ ] Column order is sensible for large new tables (8-byte columns first).
- [ ] The migration is safe on a live database ([10](10-safe-schema-migrations.md)): `NOT VALID` + `VALIDATE`, `CREATE INDEX CONCURRENTLY`, no table rewrite under heavy traffic.
